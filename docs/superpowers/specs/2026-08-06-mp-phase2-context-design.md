# Фаза 2: контекст игрока — дизайн

Дата: 2026-08-06 (ревизия после ревью того же дня)
Статус: утверждён к планированию
Родительский спек: `2026-08-04-cdda-p2p-coop-design.md`, разделы 5.3, 5.4, 10, 11 (Ф2), 12.1.
Правки родителя, следующие из этого спека: §6.4 и §13 (см. §10 ниже).

## 1. Контекст

Ф0-Ф1 сделаны: сервер со стримингом экрана и тонкий клиент работают, ворота Ф1 пройдены
(одиночная партия по сети с другой машины через Tailscale). Осталось из мультиплеерного
потока то, что нельзя проверить одним игроком: второй игрок со своим экраном, своим меню,
своим вводом.

Игровой код читает глобалы. Чтобы два игрока могли одновременно находиться в своих меню,
у каждого должен быть свой набор этих глобалов, подменяемый атомарно вместе с передачей
управления. Ф2 строит этот механизм и доказывает его безвредность на одном контексте.

**Целевая сборка — TILES.** Клиент рисует сам: тайлы карты, шрифты, размеры пикселей,
раскладка сайдбара — его дело. Сервер отдаёт данные. Это меняет не механизм контекста,
а состав того, что в контексте хранится: пиксельные и шрифтовые величины в него не попадают
вовсе. Ф2 проектируется так, чтобы переход curses → tiles менял состав входных данных,
но не механизм.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Механизм | Явная структура `player_context` + атомарное перенацеливание глобалов при активации |
| Окна игрока | Перенацеливание: контекст владеет окнами, `game`-члены переуказываются на окна активного контекста. 202 места `g->w_terrain` не трогаются |
| Метрики экрана | Не хранятся и не синхронизируются: контекст держит `viewport_params` (прислано клиентом), метрики — чистая функция от них, пересчёт на активации |
| Режимы синхронизации | Два: ре-пойнт объектов (`stdscr`, окна) и чтение через активный контекст (вьюпорт, ввод, `ui_stack`, главный адаптор). Копи-синка туда-обратно нет ни для одного поля |
| `ui_stack` | `ui_manager` держит указатель на активный стек; контексты владеют своими стеками; `active_stack` никогда не `nullptr` |
| Ввод | Per-player = очередь нажатий + таймаут в контексте. `inp_mngr` (keymap) общий, не трогаем |
| Аватар | `mp_activate_player( idx )` — единственная точка; `game::swap_slot_into_u()` становится деталью реализации и снаружи не зовётся |
| Фаза мира | Активного игрока нет; отрисовка широковещательная (`mp_for_each_context`); разрез `do_turn` на `world_turn`/`avatar_turn` — Ф3 |
| Сайдбар | Ф2 не трогает `panel_manager`; в целевом дизайне сайдбар уезжает на клиент |
| Hotseat | Слоты меняются через ту же точку `mp_activate_player`; контекст у hotseat один |
| Ворота Ф2 | Рантайм-самосравнение в **обычной** сборке, без `MULTIPLAYER` и без полной игры |
| Скоуп Ф2 | Один контекст в обеих сборках, своп тождественный |

Отвергнуто:

- **thread_local-глобалы.** `w_terrain`, `w_overmap`, `ter_view_p` — члены `game`
  (`game.h:1272-1277`), а не глобалы: `thread_local` к ним неприменим, понадобился бы
  thread_local-экземпляр всего `game`. Фаза мира исполняется без игрока и обязана рисовать
  всем — под thread_local у неё либо пустой набор, либо она должна жить в чьём-то потоке.
  Keymap грузился бы на каждого игрока вместо одного раза на процесс.
  (Аргумент «завязывает Ф3 на потоки» недействителен: родитель §5.4 сам выбирает потоки.)
- **Переезд окон в контекст с заменой `g->w_terrain` на аксессор** — 202 правки, против §12.6.
- **Пересоздание окон на свопе** — дублирует resize-путь §6.3, своп становится хрупким.
- **`game::u` через аксессор вместо контент-свопа** — архитектурно чище всего, своп исчезает
  как явление, но тысячи обращений `g->u` по дереву. Пересматривается только по результату
  замера стоимости свопа (§8.5).
- **Инстанс `panel_manager` на контекст** — работу выбрасывает целиком переход к клиентскому
  сайдбару (§6.5).
- **Выделенный контекст фазы мира со своим экраном** — мировые анимации не видит никто (§6.4).

## 3. Структура контекста

`src/mp/mp_context.h` / `.cpp`.

```cpp
// Всё, что нужно знать серверу о дисплее игрока. Прислано клиентом, единственный
// вход для расчёта метрик. Пикселей, шрифтов, тайлсета и DPI здесь нет и не будет:
// это клиентские величины.
struct viewport_params {
    // Текстовая сетка UI, в клетках.
    int term_cols = 0, term_rows = 0;
    // Отношение «клетка текста : тайл карты», по горизонтали и вертикали.
    // В curses все четыре равны 1. В TILES клиент присылает свои значения; сервер
    // трактует их как безразмерное отношение, а не как пиксели.
    int font_units = 1, tile_units = 1;
    int font_units_v = 1, tile_units_v = 1;
};

struct player_context {
    // Аватар: индекс в game::player_slots.
    size_t slot_index = 0;

    // Параметры дисплея игрока.
    viewport_params viewport;

    // Экран: корневое окно игрока. В серверной сборке — композитный буфер;
    // в обычной — тот же stdscr терминала.
    catacurses::window stdscr;

    // Окна игрока и владеющие копии (game.h:1327-1328 держит их сейчас).
    catacurses::window w_terrain, w_overmap, w_omlegend, w_minimap, w_pixel_minimap;
    catacurses::window w_terrain_ptr, w_minimap_ptr;

    // Вью-стейт. Читается через активный контекст, не копируется в game.
    tripoint_bub_ms ter_view_p;
    point_rel_ms driving_view_offset;

    // Ввод игрока: очередь нажатий и таймаут. Keymap (`inp_mngr`) общий.
    std::deque<input_event> input_queue;
    int input_timeout_ms = -1;

    // Открытые UI игрока.
    ui_stack_t ui_stack;

    // Главный ui_adaptor игрока: он создаёт окна и метрики этого контекста.
    // shared_ptr держит игровой цикл игрока (main.cpp:689).
    weak_ptr_fast<ui_adaptor> main_ui_adaptor;
};
```

### 3.1 Метрики не хранятся

`TERMX`, `TERMY`, `TERRAIN_WINDOW_*`, `OVERMAP_WINDOW_*`, `OVERMAP_LEGEND_WIDTH`,
`FULL_SCREEN_WIDTH/HEIGHT`, `POSX`, `POSY` (`output.h:127-143`) остаются глобалами и
**вычисляются**, а не синхронизируются:

```
mp_apply_viewport_params( ctx )   // единственный писатель этих глобалов
```

Формула экстента — существующая, `w * font_units / tile_units`: это тело
`to_map_font_dim_width` (`sdltiles.cpp:6754`), только числа берутся из контекста, а не из
глобалов `fontwidth`/`map_font_width()`. Направление одно, обратного пути нет, забыть
поле в «одной из сторон» невозможно по построению.

В серверной сборке `to_map_font_dimension` не вызывается вовсе: пересчёт единиц — работа
того, кто заполняет `viewport_params`, то есть клиента.

`TERMX`/`TERMY` в обычной TILES-сборке пишутся в опции `TERMINAL_X/Y` с сохранением на диск
(`game.cpp:550-552`). В серверной сборке эта запись должна быть закрыта: иначе размер окна
подключившегося клиента затирает конфиг сервера.

## 4. Своп

`mp_activate_player( size_t idx )` — единственный писатель глобальных алиасов:

1. **Аватар.** Снять текущий, поставить новый:
   `if( current != 0 ) swap_slot_into_u( current ); if( idx != 0 ) swap_slot_into_u( idx );`
   `game::swap_slot_into_u()` (`game.cpp:4666-4681`) self-inverse и корректна **только парой**
   вызовов с одним индексом — поэтому она становится приватной деталью и снаружи не зовётся
   никем, включая hotseat (`mp_hotseat_loop.cpp:34,75` переходит на `mp_activate_player`).
   Инвариант: `player_slots[active] == &u`, проверяется `cata_assert` в дебаг-сборке.
2. `catacurses::stdscr = ctx->stdscr` — ре-пойнт (прецедент: `mp_curses_server.cpp:111`).
3. `g->w_terrain = ctx->w_terrain`, то же для `w_overmap`, `w_omlegend`, `w_minimap`,
   `w_pixel_minimap`, `w_terrain_ptr`, `w_minimap_ptr` — ре-пойнт.
4. `mp_apply_viewport_params( ctx )` — пересчёт метрик (§3.1).
5. `ui_manager::set_active_stack( &ctx->ui_stack )`.
6. `mp_set_active_context( ctx )` — вьюпорт и ввод: `g->ter_view_p`/`driving_view_offset`
   читаются через активный контекст; серверный бэкенд `input_manager::get_input_event()`
   читает `input_queue`/`input_timeout_ms` активного контекста.

`mp_activate_world()` — вход в фазу мира: активного игрока нет (§6.4).

### 4.1 Условие корректности локального кэша

Код, положивший `g->w_terrain` в локальную переменную и продолживший после передачи
управления, получает **верное** окно: игрок просыпается вместе с обратным свопом, и всё
время ожидания его локальная копия указывала на его же окно. Это следствие двух свойств,
а не свойство ре-пойнта:

1. исполняется только держатель эстафеты;
2. активация и деактивация парны.

Оба проверяемы. Ф3 добавляет дебаг-ассерт «исполняется только держатель эстафеты»
(сравнение `std::this_thread::get_id()` с владельцем): сторожевой таймер §5.4 родителя ловит
«держит слишком долго», ассерт — «исполняется, не держа». Ослабление любого из двух свойств
превращает локальный кэш из корректного в гонку по указателю на чужое окно.

Настоящая протечка в этом месте одна и другая: **статические локали меню** (запомненный
курсор, последний фильтр) общие между игроками. Косметика, принимается осознанно (§5.3
родителя).

## 5. ui_manager и ввод

### 5.1 ui_manager

Сейчас: `static ui_stack_t ui_stack` (`ui_manager.cpp:36`), ~20 использований. Меняется на
указатель активного стека:

- `static ui_stack_t *active_stack`; `ui_adaptor` конструкторы/деструкторы и redraw-пути
  итерируют `active_stack`.
- Тип `ui_stack_t` (`ui_manager.cpp:24`) переезжает в `ui_manager.h` — контексту нужен
  этот тип для поля `ui_stack`.
- `ui_manager::set_active_stack( ui_stack_t * )` — единственный сеттер, вызывается из
  `mp_activate_player` / `mp_activate_world`.
- **`active_stack` никогда не `nullptr`.** На время фазы мира он указывает на выделенный
  стек мира — заглушку для аварийных UI (`debugmsg`, `ui_manager.cpp:50-60`), рисуемых
  широковещательно. Это не «контекст мира» из отвергнутых вариантов: анимации мира туда
  не адресуются (§6.4).
- Транзиентные флаги (`redraw_in_progress`, `showing_debug_message`, `imgui_frame_started`,
  `restart_redrawing`) остаются глобалами: они per-redraw, а не per-player. В строгой эстафете
  своп происходит в точках ожидания ввода, где редра нет.

### 5.2 Инвариант владения стеком

`ui_adaptor` регистрирует себя в **активном** стеке при конструировании
(`ui_manager.cpp:42,49,86`) и снимает себя из **активного** при разрушении (`:109-113`).
Отсюда инвариант:

> `ui_adaptor` рождается и умирает под тем же активным контекстом.

При строгой эстафете он выполняется сам собой: код игрока исполняется только пока игрок
активен. Нарушение молчаливое — деструктор не находит себя, выходит по `break`, и в родном
стеке остаётся `reference_wrapper` на уничтоженный объект.

Поэтому инвариант проверяется, а не только декларируется: `ui_adaptor` запоминает при
конструировании `ui_stack_t *owner`, деструктор в дебаг-сборке делает
`cata_assert( owner == active_stack )`. Один указатель на объект; ловит весь класс ошибок в
точке возникновения и без второго игрока.

`ui_adaptor` объекты живут на C++-стеке UI-кода; стек хранит `reference_wrapper`, поэтому
парковка стека игрока в его контексте не инвалидирует рефы. Приём `debug_message` на
неактивном стеке — известный край в Ф3; в серверной сборке `debugmsg` и так не модален
(§9 родителя).

### 5.3 Ввод

Per-player часть `inp_mngr` — очередь нажатий и таймаут — лежит в контексте. Keymap
(`input_manager` как таковой) общий: §13 родителя, все играют с раскладкой сервера.

- Серверный бэкенд `input_manager::get_input_event()` (`mp_curses_server.cpp:135`) вместо
  `mp_server_wait_for_input( input_timeout_ms )` читает активный контекст.
- `input_manager::set_timeout` в серверной сборке пишет в активный контекст.
- Обычная сборка: бэкенд ncurses/SDL как был; контекстная очередь не используется — один
  игрок читает клавиатуру напрямую.

Рефактор `input_manager` не нужен.

## 6. Интеграция

### 6.1 Владение и создание

`game` держит `std::vector<player_context>` параллельно `player_slots`. Ф2 — размер 1.

`mp_ensure_player_context()` создаёт `context[0]` и вызывает `mp_activate_player(0)`.
Точка входа: старт партии в обычной сборке; `hello`/`resize` клиента в серверной.

### 6.2 Переезд создания окон

Окна сейчас создаются в resize-колбэке главного `ui_adaptor` (`game.cpp:3181-3230`) с
установкой метрик. Колбэк разделяется на две части:

- `mp_apply_viewport_params( ctx )` — только метрики (§3.1), вызывается и на свопе, и на резайзе;
- `mp_resize_active_context()` — метрики плюс создание окон контекста, вызывается только
  на настоящем резайзе.

Алиасы в `game` держит `mp_activate_player`.

### 6.3 Главный ui_adaptor и инвалидация

`main_ui_adaptor` переезжает из `game` (`game.h:1380`) в контекст (§3).

`invalidate_main_ui_adaptor()` и `mark_main_ui_adaptor_resize()` становятся
**широковещательными**: проходят по всем контекстам. Это верная семантика, а не приближение —
значительная часть из ~90 вызовов идёт из мирового кода (`map.cpp:1267`,
`animation.cpp:68,921`, `teleport.cpp:154`, `mattack_actors.cpp:680`, `do_turn.cpp:252`), и
взрыв видят все, кто на него смотрит. Флаг ленивый: перерисовка случится, когда контекст
получит эстафету. Ни один из ~90 сайтов не трогается и не классифицируется.

### 6.4 Фаза мира

Родитель §5.4: исполняется либо контекст игрока, либо фаза мира. Ф2 фиксирует два понятия,
Ф3 их реализует:

- **Активного игрока нет.** `mp_activate_world()` ставит стек мира (§5.1) и снимает алиасы
  игрока. Контекст мира — не экран: у него нет ни окон, ни вьюпорта.
- **Мир рисует широковещательно.** `mp_for_each_context( fn )`: ре-пойнт окон → выполнить →
  следующий. Точек мало и они локальны: `animation.cpp:69-70`, `do_turn.cpp:266,754`.

Разрез `do_turn` — работа Ф3, но записан здесь, потому что определяет форму API:
`do_turn.cpp` сегодня перемешивает мировые шаги с per-avatar кодом
(`do_turn.cpp:735-775`: `mon_info_update`, `u.process_turn`, `handle_weather_effects`,
`handle_progress_ui`, `u.update_bodytemp`, `u.update_body_wetness`, `u.apply_wetness_morale`,
`u.update_morale`). Целевая форма — `world_turn()` один раз без активного игрока и
`avatar_turn( avatar & )` по разу на игрока под его контекстом.

Тот же разрез попутно чинит известный дефект hotseat: доводка в `mp_hotseat_loop.cpp:88-91`
зовёт для слотов 1+ только `process_turn()`, поэтому у них не обновляются температура тела,
промокание, мораль и `mon_info`. Отдельно не чинится — hotseat не в приоритете; записано,
чтобы разрез Ф3 не пришлось объяснять заново.

### 6.5 Сайдбар

Ф2 `panel_manager` не трогает: в контекст он не едет, инстанс на игрока не заводится.

Целевое состояние — сайдбар считает и рисует клиент: разрез внутри `widget` на
`widget::sample( ava ) → widget_values` (сервер) и `widget::layout( widget_values, max_width )`
(клиент), состав сайдбара приходит в `hello`, дальше летят значения. На сервере
`sidebar_left/right` становятся нулём, и деление экрана перестаёт быть его заботой —
вместе с этим отпадают поля `font_units`/`tile_units` из `viewport_params`.

До того сайдбар рисуется ячейками общим менеджером сервера. Следствие, которое надо закрыть
сразу: пункт настройки сайдбара (`show_adm()`, `panels.cpp:857-869`) в серверной сборке
недоступен — на общем менеджере он меняет ширину и дёргает `mark_main_ui_adaptor_resize()`,
то есть двигает вьюпорт всем посреди чужого хода.

### 6.6 Границы общего и персонального

Явное правило: **опции общие, кроме перечисленных**.

| Что | Где живёт |
|---|---|
| Раскладка клавиш | Сервер, общая (§13 родителя) |
| Раскладка панелей | Сервер, общая; в целевом дизайне — клиент (§6.5) |
| Шрифт, тайлсет, размер окна, DPI | Клиент, всегда |
| Размер терминала | Клиент присылает, сервер хранит в контексте |

### 6.7 Сборки

Контекст и своп собираются всегда (один контекст в обычной игре — ровно как слот нулевой).
Под `MULTIPLAYER` — планировщик, сеть, серверный бэкенд (Ф3 и дальше).

## 7. Тестирование

Ворота Ф2: 266 тестовых файлов зелёные + механико-уровневый самосравненец **в обычной
сборке**.

1. **`mp_context_test.cpp`** — юнит контекста и свопа:
   - `mp_activate_player(0)` тождественен: `stdscr`, `u`, окна, метрики не изменились;
   - `A → B → A` на слотах: содержимое слотов после возврата совпадает с исходным
     (ловит непарный `swap_slot_into_u`, который на `idx == 0` невидим);
   - вьюпорт: запись в вьюпорт активного контекста не видна другому контексту.
2. **`mp_context_swap_test.cpp`** — самосравненец без полной игры и без `MULTIPLAYER`:
   - два контекста A и B, у каждого своё корневое `catacurses`-окно в роли `stdscr`;
   - скриптовые `ui_adaptor` redraw-колбэки, рисующие клетки в активный `stdscr`;
   - последовательность: активировать A, рисовать сценарий A, снять содержимое; активировать
     B, рисовать сценарий B, снять; активировать A снова, повторить сценарий A, снять A';
   - assert: `A == A'` **по содержимому ячеек окна** (не по указателям и не по флагам),
     B соответствует своему сценарию;
   - протёкший глобал (`stdscr`, `ui_stack`, окно вне контекста) меняет картину и виден сразу.
3. **Регресс:** 266 тестовых файлов зелёные — критерий, что рефактор ничего не сломал.

Ворота не зависят от `MULTIPLAYER`-сборки: механизм контекста прогоняется в CI обычной
конфигурацией.

Не входит в Ф2: тяжёлые меню (инвентарь, крафт, карта, персонаж, транспорт, стройка),
сессионный харнесс, `status`-сообщение, TSAN-прогон эстафеты — всё это Ф3+.

## 8. Риски

1. **Пропущенный per-player глобал.** Главный класс ошибок. Метрики закрыты по построению
   (§3.1: вычисляются из одного входа, а не синхронизируются), но список объектов —
   по-прежнему конечный перебор. Механико-тест §7 ловит протечки на ранней стадии.
2. **Переезд создания окон.** Единственный содержательный рефактор существующего пути
   (`game.cpp` resize-колбэк). Митигируется 266 тестами и самосравненцем.
3. **Нарушение инварианта владения стеком.** Закрыто дебаг-ассертом (§5.2).
4. **Гниение пути.** Контекст живёт в обеих сборках; один контекст прогоняется всеми тестами,
   и ворота Ф2 больше не требуют серверной сборки.
5. **Стоимость свопа не измерена.** Своп аватара — три move целого `avatar`
   (`game.cpp:4676-4678`), и с разрезом `avatar_turn` (§6.4) это N свопов на тик, то есть
   горячий путь, а не разовая операция при старте. Замерить в Ф3; при плохом результате
   пересмотреть в пользу аксессора вместо контент-свопа (§2, «Отвергнуто»).

## 9. Границы

- Один контекст; второй игрок и своп на эстафете — Ф3.
- Разрез `do_turn` на `world_turn`/`avatar_turn` — Ф3; Ф2 только называет механизм.
- `mp_server_screen` остаётся модулем на одну сессию; превращение в объект на сессию
  (грид, транспорт, размер, бэклог) — Ф3, где есть второй клиент, на котором это проверяется.
- Сетевой протокол не меняется; `status`-сообщение остаётся долгом Ф4.
- Клиентский сайдбар и разрез `widget::sample`/`layout` — tiles-фаза.
- Раскладки, звук — как в родителе, вне скоупа.

## 10. Требуемые правки родительского спека

Следуют из решения делать целевую сборку на тайлах; лучше внести один раз, чем ловить
по частям:

- **§6.4** — «Содержимое игры и моды не сверяются: клиенту они не нужны» перестаёт быть
  верным. Тайлы требуют совпадения ID предметов, монстров и террейна; клиентский сайдбар —
  совпадения JSON-определений виджетов. Клиент обязан совпадать с сервером по контенту
  и модам, сверка возвращается в протокол.
- **§13** — «TILES для сетевой игры нет» пересматривается: тайлы становятся целевым режимом,
  а не отложенной возможностью. Поток описания вьюпорта, названный там «дверью, которую
  оставляем открытой», перестаёт быть гипотетическим.
