# Фаза 2: контекст игрока — дизайн

Дата: 2026-08-06
Статус: утверждён к планированию
Родительский спек: `2026-08-04-cdda-p2p-coop-design.md`, разделы 5.3, 5.4, 10, 11 (Ф2), 12.1.

## 1. Контекст

Ф0-Ф1 сделаны: сервер со стримингом экрана и тонкий клиент работают, ворота Ф1 пройдены
(одиночная партия по сети с другой машины через Tailscale). Осталось из мультиплеерного
потока то, что нельзя проверить одним игроком: второй игрок со своим экраном, своим меню,
своим вводом.

Игровой код читает глобалы. Чтобы два игрока могли одновременно находиться в своих меню,
у каждого должен быть свой набор этих глобалов, подменяемый атомарно вместе с передачей
управления. Ф2 строит этот механизм и доказывает его безвредность на одном контексте.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Механизм | Явная структура `player_context` + атомарное перенацеливание глобалов при активации |
| Окна игрока | Перенацеливание: контекст владеет окнами, `game`-члены переуказываются на окна активного контекста. ~275 мест `g->w_terrain` не трогаются |
| Синхронизация полей | Три режима: ре-пойнт (объекты), копи-синк туда-обратно (значения), прямое чтение через активный контекст (стек UI, ввод) |
| `ui_stack` | `ui_manager` держит указатель на активный стек; контексты владеют своими стеками |
| Ввод | Per-player = очередь нажатий + таймаут в контексте. `inp_mngr` (keymap) общий, не трогаем |
| Точка свопа | `mp_activate_player( idx )`, единственный писатель глобальных алиасов |
| Hotseat | Не трогаем: общий экран, слоты меняют только аватар через `swap_slot_into_u` |
| Снимки экранов (ворота) | Рантайм-самосравнение на уровне механики, без полной игры |
| Скоуп Ф2 | Один контекст в обеих сборках, своп тождественный |

Отвергнуто: thread_local-глобалы (противоречит тексту §5.3 «подменяемый атомарно», завязывает
Ф3 на потоки, требует выделенного контекста фазы мира, дублирует keymap-лоад); переезд окон
в контекст с заменой `g->w_terrain` на аксессор (275 правок, против §12.6); пересоздание окон
на свопе (дублирует resize-путь §6.3, своп становится хрупким).

## 3. Структура контекста

`src/mp/mp_context.h` / `.cpp`. Полный набор полей, раздел §5.3 плюс известные per-terminal
глобалы из пути отрисовки:

```cpp
struct player_context {
    // Аватар: индекс в game::player_slots; синк через существующий
    // game::swap_slot_into_u() (контент-своп, self-inverse).
    size_t slot_index = 0;

    // Экран: корневое окно игрока. В серверной сборке — композитный буфер
    // (mp_server_screen); в обычной — тот же stdscr терминала.
    catacurses::window stdscr;

    // Окна игрока, размеры соответствуют его терминалу (§6.3 родителя).
    catacurses::window w_terrain, w_overmap, w_omlegend, w_minimap, w_pixel_minimap;

    // Вью-стейт, копи-синк (как avatar content в swap_slot_into_u).
    tripoint_bub_ms ter_view_p;
    point_rel_ms driving_view_offset;

    // Размеры terrain-окна и позиция персонажа в нём — per-terminal глобалы.
    int TERRAIN_WINDOW_WIDTH, TERRAIN_WINDOW_HEIGHT,
        TERRAIN_WINDOW_TERM_WIDTH, TERRAIN_WINDOW_TERM_HEIGHT;
    int POSX, POSY;

    // Ввод игрока: очередь нажатий и таймаут. Keymap (`inp_mngr`) общий.
    std::deque<input_event> input_queue;
    int input_timeout_ms = -1;

    // Открытые UI активного игрока.
    ui_stack_t ui_stack;
};
```

Известные per-player глобалы, попавшие в контекст: `TERRAIN_WINDOW_*`, `POSX`, `POSY`
(~100 рефов, зависят от размера терминала). Полнота набора не гарантируется списком —
проверяется механико-уровневым тестом §7.

## 4. Своп

`mp_activate_player( size_t idx )` — единственный писатель глобальных алиасов:

1. `g->swap_slot_into_u( idx )` — аватар.
2. `catacurses::stdscr = ctx->stdscr` — ре-пойнт (прецедент: mp_curses_server.cpp:111).
3. `g->w_terrain = ctx->w_terrain`, то же для `w_overmap`, `w_omlegend`, `w_minimap`,
   `w_pixel_minimap` — ре-пойнт.
4. `g->ter_view_p = ctx->ter_view_p`, `g->driving_view_offset = ctx->driving_view_offset`,
   копи-синк туда; на деактивации обратно. `TERRAIN_WINDOW_*`/`POSX`/`POSY` — копи-синк так же.
5. `ui_manager::set_active_stack( &ctx->ui_stack )`.
6. `mp_set_active_context( ctx )` — ввод: серверный бэкенд `input_manager::get_input_event()`
   читает `input_queue`/`input_timeout_ms` активного контекста.

Три режима синхронизации полей: **ре-пойнт** (объекты — stdscr, окна; присваивание
shared_ptr-обёртки, дешёво), **копи-синк туда-обратно** (значения — view-стейт, размеры;
тот же приём, что avatar в swap_slot_into_u), **прямое чтение через активный контекст**
(ui_stack, ввод — нет смысла держать глобальную копию).

Застарелый алиас через своп (код закэшировал `g->w_terrain` до передачи управления и
продолжил после) — ошибка в любом механизме: чтение через имя всегда даёт активного игрока.
Дизайн принимает это как косметическую протечку, как статические локали меню (§5.3 родителя).

## 5. ui_manager и ввод

### 5.1 ui_manager

Сейчас: `static ui_stack_t ui_stack` (ui_manager.cpp:36), ~20 использований. Меняется на
указатель активного стека:

- `static ui_stack_t *active_stack`; `ui_adaptor` конструкторы/деструкторы и redraw-пути
  итерируют `active_stack`.
- Тип `ui_stack_t` (`using ui_stack_t = std::vector<std::reference_wrapper<ui_adaptor>>`,
  сейчас file-static в ui_manager.cpp:24) переезжает в `ui_manager.h` — контексту нужен
  этот тип для поля `ui_stack`.
- `ui_manager::set_active_stack( ui_stack_t * )` — единственный сеттер, вызывается из
  `mp_activate_player`.
- Транзиентные флаги (`redraw_in_progress`, `showing_debug_message`, `imgui_frame_started`,
  `restart_redrawing`) остаются глобалами: они per-redraw, а не per-player. В строгой эстафете
  своп происходит в точках ожидания ввода, где редра нет.

`ui_adaptor` объекты живут на C++-стеке UI-кода; стек хранит `reference_wrapper`, поэтому
парковка стека игрока в его контексте не инвалидирует рефы. Приём `debug_message` (`showing_debug_message`)
на неактивном стеке — известный край в Ф3; в серверной сборке `debugmsg` и так не модален
(§9 родителя).

### 5.2 Ввод

Per-player часть `inp_mngr` — очередь нажатий и таймаут — лежит в контексте. Keymap
(`input_manager` как таковой) общий: §13 родителя, все играют с раскладкой сервера.

- Серверный бэкенд `input_manager::get_input_event()` (mp_curses_server.cpp:135) вместо
  `mp_server_wait_for_input( input_timeout_ms )` читает активный контекст.
- `input_manager::set_timeout` в серверной сборке пишет в активный контекст.
- Обычная сборка: бэкенд ncurses/SDL как был; контекстная очередь не используется — один
  игрок читает клавиатуру напрямую.

Рефактор `input_manager` не нужен.

## 6. Интеграция

- **Владение.** `game` держит `std::vector<player_context>` параллельно `player_slots`.
  Ф2 — размер 1.
- **Создание контекста:** `mp_ensure_player_context()` создаёт `context[0]` и вызывает
  `mp_activate_player(0)`. Точка входа: старт партии в обычной сборке; `hello`/`resize`
  клиента в серверной.
- **Переезд создания окон.** Окна сейчас создаются в resize-колбэке главного `ui_adaptor`
  (game.cpp:3185-3234) с установкой `TERRAIN_WINDOW_*`/`POSX`/`POSY`. Эти глобалы и окна
  становятся членами контекста; колбэк переписывается в `mp_resize_active_context( term_size )`,
  который пересчитывает размеры в контекст и создаёт окна контекста. Алиасы в `game` держит
  `mp_activate_player`.
- **Точка свопа.** Ф2 — один вызов на старте. Полный своп на передаче эстафеты — Ф3.
- **Hotseat не трогаем.** Общий экран, слоты меняют только аватар через `swap_slot_into_u`.
  Контекст у hotseat один.
- **Сборки.** Контекст и своп собираются всегда (один контекст в обычной игре — ровно как
  слот нулевой). Под `MULTIPLAYER` — планировщик, сеть, серверный бэкенд (Ф3 и дальше).

## 7. Тестирование

Ворота Ф2: 266 тестовых файлов зелёные + механико-уровневый самосравненец.

1. **`mp_context_test.cpp`** (обычная сборка) — юнит контекста и свопа:
   - `mp_activate_player(0)` тождественен: `stdscr`, `u`, окна, `TERRAIN_WINDOW_*`,
     `POSX`/`POSY` не изменились;
   - копи-синк: запись в `g->ter_view_p` → деактивация → чтение из контекста → активация →
     `g->ter_view_p` восстановлен.
2. **`mp_context_swap_test.cpp`** (MP_SERVER, механика) — самосравненец без полной игры:
   - два идентичных контекста A и B, каждый со своим композит-буфером (stdscr = composite);
   - скриптовые `ui_adaptor` redraw-колбэки, рисующие клетки в активный stdscr;
   - последовательность: активировать A, рисовать сценарий A, захват буфера; активировать B,
     рисовать сценарий B, захват; активировать A снова, повторить сценарий A, захват A';
   - assert: `A == A'` (возврат в контекст идеально восстанавливает экран), B соответствует
     своему сценарию;
   - протёкший глобал (stdscr/ui_stack/окно вне контекста) меняет картину и виден сразу.
3. **Регресс:** 266 тестовых файлов зелёные — критерий, что рефактор ничего не сломал.

Не входит в Ф2: тяжёлые меню (инвентарь, крафт, карта, персонаж, транспорт, стройка),
сессионный харнесс, `status`-сообщение, TSAN-прогон эстафеты — всё это Ф3+.

## 8. Риски

1. **Пропущенный per-player глобал.** Главный класс ошибок. Список из §3 конечный, но не
   гарантирует полноту; механико-тест §7 ловит протечки на ранней стадии. `TERRAIN_WINDOW_*`
   и `POSX`/`POSY` уже внесены — они не были в списке §5.3 родителя.
2. **Переезд создания окон.** Единственный содержательный рефактор существующего пути
   (game.cpp resize-колбэк). Митигируется 266 тестами и самосравненцем.
3. **Застарелый алиас через своп.** Принят как косметическая протечка (§4).
4. **Гниение пути.** Контекст живёт в обеих сборках; один контекст прогоняется всеми тестами.

## 9. Границы

- Один контекст; второй игрок и своп на эстафете — Ф3.
- Сетевой протокол не меняется; `status`-сообщение остаётся долгом Ф4.
- Раскладки, звук, TILES — как в родителе, вне скоупа.
