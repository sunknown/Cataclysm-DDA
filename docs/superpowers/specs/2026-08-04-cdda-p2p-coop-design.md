## 1. Контекст

Предыдущий спек проектировал кооператив как lockstep с реплеем намерений: сервер и все
клиенты гоняют идентичную полную симуляцию, по сети идут действия игроков. Две разведки
опровергли эту модель измерением.

**MVP-0, проба детерминизма** (`docs/superpowers/reports/2026-07-31-mvp0-determinism-findings.md`).
Один и тот же бинарь с одним сидом воспроизводится побитово. Сборки разными компиляторами
расходятся за 1–11 ходов, причём расходится **число обращений к RNG** — то есть сборки уходят
по разным ветвям кода. Гипотеза о контракции FMA опровергнута экспериментом; главный кандидат
(неспецифицированный порядок вычисления аргументов, 51 место в `src/*.cpp`) не доказан.
Стоимость межсборочного детерминизма оценена в 8–20 дней с существенным риском роста.

**MVP-1, разведка разрезаемости** (`docs/superpowers/reports/2026-07-31-mvp1-choose-execute-separability.md`).
Инвариант «`apply_intent` не открывает окон» проверен на десяти тяжёлых действиях. Три получили
вердикт «не режется»: крафт (1 M-обращение, 22 A), управление транспортом (5 M), строительство
(2 M, 5 A). Все три — стержневые механики. Решение по воротам: пересматривать дизайн.

**MVP-2, hotseat** — выполнен и работает: два полноценных `avatar` в одном бабле, цикл хода
с фиксированным порядком слотов, якорь бабла по целочисленной середине, тезер, миграция
симуляционного кода на `nearest_player`/`any_player`, сохранение нескольких слотов в сейве.
Это доказало, что второй аватар не разваливает игру, и дало фундамент, который переиспользуется
целиком.

Настоящий спек описывает модель, в которой оба опровергнутых требования отсутствуют
не потому, что их обошли, а потому, что они не возникают.

## 2. Скоуп

### В скоупе

- Кооператив на N игроков (играбельность проверяется на 2–4) в одном мире.
- Выделенный сервер с единственной авторитетной симуляцией, все игроки — клиенты.
- Тонкий клиент: сервер гоняет весь UI каждого игрока и стримит ему экран.
- Одновременная игра: у каждого игрока свой контекст, меню одного не морозит остальных.
- Барьер хода с ленивым таймаутом и режимом «ходите без меня».
- Tethered-кооп: все игроки в пределах одного reality bubble.

### Вне скоупа

- TILES для сетевой игры (первый этап — только curses).
- Звук у клиентов.
- Персональные клавиатурные раскладки (первый этап — раскладка сервера).
- Free-roam, PvP, шифрование, аутентификация, матчмейкинг, обход NAT.

## 3. Сводка принятых решений

| Решение | Выбор |
|---|---|
| Топология | Выделенный сервер, все игроки — удалённые клиенты |
| Модель симуляции | Единственная авторитетная симуляция на сервере |
| Формат провода | Ячейки экрана от сервера, нажатия от клиента |
| Кодировка | Гибрид: управление JSON через `JsonOut`, экран компактным бинарём |
| Транспорт | Свои BSD-сокеты плюс шим под Winsock, `TCP_NODELAY` обязателен |
| imgui на сервере | Через вендоренный `imtui`: кадр в `ImTui::TScreen`, оттуда в буфер ячеек |
| Клиент | Тот же бинарь в режиме `--connect`; ни мира, ни контента, ни правил — только карточка персонажа (§8.2) |
| Режим отрисовки | curses в первых фазах; тайлы — целевой режим, а не отложенная возможность (§13) |
| Одновременность | Контекст на игрока, переключение в точках ожидания ввода |
| Механизм переключения | Потоки со строгой эстафетой (фиберы — запасной вариант); отдельного потока ввода-вывода нет (§5.4) |
| Барьер | Бесконечный, пока никто не упёрся; активность или назначенный маршрут считаются ходом; «тороплю» запускает отсчёт; в бою автоматически |
| AFK | Добровольный режим «ходите без меня», он же результат обрыва связи |
| Долгие активности | Свободный прогон тиков, когда все заняты и никто не держит барьер |
| Детерминизм | Не требуется |
| Тип мира | Обычный, по файлу сейва на персонажа; любого персонажа можно играть и в соло, и в кооп |
| Вход в сессию | Меню входа на каждом клиенте; состав фиксируется в момент старта партии |
| Сеть | LAN и VPN-оверлеи (Tailscale/ZeroTier), RTT десятки миллисекунд |

## 4. Что отменяется вместе с lockstep

Перечислено явно, потому что это основная экономия проекта.

- **Требование детерминизма целиком.** Симуляция одна — расходиться нечему. Умирают §7 старого
  спека (аудит порядка итераций по неупорядоченным контейнерам, вынос RNG из UI-путей,
  `stable_sort` в сим-путях, аудит указателей, фиксация флагов плавающей точки), §7.2 (лёгкий
  и глубокий хеши состояния), §7.3 (детект десинка и лечение пересылкой сейва), риск §10.2.
- **Инвариант «`apply_intent` не открывает окон» и фаза Ф1** (5–8 недель). M-обращения перестают
  быть проблемой: сервер, дойдя до `query_yn` посреди крафта, спрашивает того клиента, чей это
  персонаж, и ждёт ответа в его контексте. Крафт, вождение и строительство работают без правок.
- **Слой намерений** `mp_intent`, буферы намерений, детерминированный порядок исполнения.
- **Голосование за скип и батчи по 100 тиков** (§5.8). Существовали только затем, чтобы
  независимые симуляции не расходились.
- **Фаззер намерений и харнесс сверки хешей** (§8).
- **Требование одинаковых билдов и модов у всех участников** (§6.1). Клиент не содержит игрового
  контента; сверяется только версия протокола.

Из уже выполненной работы не пропадает ничего: слоты игроков, якорь бабла, тезер и миграция
симуляции на `nearest/any player` нужны в новой модели ровно так же.

## 5. Архитектура

### 5.1 Роли

**Сервер** — процесс с полной симуляцией без графики. Вместо SDL и ncurses линкуется собственная
curses-реализация проекта (`src/cursesport.h`, `src/cursesport.cpp`) — та, что уже используется
TILES- и Windows-сборками, где `WINDOW` это буфер ячеек в памяти с флагом `touched` на каждой
строке. Сервер реализует два бэкендных шва:

- `curses_drawwindow()` — вместо рисования пишет изменившиеся строки в композитный буфер
  экрана владельца окна и помечает область грязной;
- `input_manager::get_input_event()` (`src/input.h:335`) — вместо чтения клавиатуры отдаёт
  управление планировщику и возвращается, когда от этого клиента придёт нажатие.

Оба места уже являются точками расширения бэкенда: существуют реализации для ncurses
(`src/ncurses_def.cpp:426`), SDL (`src/sdltiles.cpp:6444`) и Windows (`src/wincurse.cpp:704`).
Серверная — четвёртая.

Поскольку бэкенд выбирается на этапе линковки, сервер — **отдельная цель сборки**
(`cataclysm-server`), а не режим клиентского бинаря. Готовиться к одной шероховатости:
`src/cursesport.h` закрыт условием `#ifndef TUI`, а `TUI` определяется при
`!(TILES || WIN32)` — то есть headless-сборка под Linux сейчас получает ncurses, а не
буферную реализацию. Серверной цели нужен собственный признак сборки в этом условии.

Два шва — это два места, где кончается сеть, но не весь объём бэкенда. Как и любой из трёх
существующих, серверный обязан определить ещё около двадцати символов платформенной обвязки:
`init_interface`, `endwin`, `supports_256_colors`, `pump_events`, `set_timeout`,
`input_context::get_coordinates`, `gamepad_available`, `handle_resize`, `resize_term`,
`projected_window_*`, `get_terminal_*`, `refresh_display`, `drain_renderer_recovery`,
`refresh_mouse_config`, `set_title`, `get_scaling_factor`. Почти все — тривиальные заглушки,
но список надо снять с `src/wincurse.cpp` целиком, а не угадывать.

**imgui — третий шов, и он не тривиален.** Значительная часть интерфейса (крафт, инвентарь,
попапы — 19 файлов в `src/`) рисуется через imgui, а не через curses. В текстовом режиме
проект уже рендерит его вендоренным `imtui`: `imtui-impl-text.cpp` кладёт кадр в
`ImTui::TScreen`, а `imtui-impl-ncurses.cpp` отдельно выкладывает этот буфер в curses
(`src/third-party/imtui/imtui-impl-ncurses.cpp:428`). Серверу нужен третий выкладыватель — в
композитный буфер ячеек. Отсюда два следствия: серверная цель определяет `IMTUI`, но при этом
**не** должна определять `TUI` (условие в `src/cursesport.h` учитывает оба), и `src/cata_imgui.cpp`
получает развилку выбора бэкенда — единственная содержательная правка в существующем файле
во всей фазе Ф0.

**Клиент** — тот же бинарь в режиме `--connect host:port`. Не создаёт `game`, не грузит
JSON-контент, не читает и не пишет сейвы, не знает ни одного игрового правила. Соединяется,
применяет присланные ячейки к своему экрану, отправляет ввод. Работает в любой обычной
сборке — ncurses, TILES, Windows, — потому что от игры ему не нужно ничего.

**Симуляция о сети не знает.** Она не знает даже, что игроков несколько, — в той же мере,
в какой уже не знает в hotseat. Вся сеть кончается на бэкенде curses и на планировщике.

### 5.3 Контекст игрока

Игровой код читает глобалы. Чтобы два игрока могли одновременно находиться в своих меню,
у каждого должен быть свой набор этих глобалов, подменяемый атомарно вместе с передачей
управления.

| Что | Где сейчас |
|---|---|
| Аватар | `game::u` и `player_slots`; подмена уже написана — `game::swap_slot_into_u()` |
| Экран | `catacurses::stdscr` (`src/cursesdef.h:111`) |
| Стек UI и флаги перерисовки | `ui_stack` и `static bool` в `src/ui_manager.cpp:26-36` |
| Ввод | `inp_mngr` (`src/input.h:452`) — очередь нажатий и таймаут |
| Окна игры | `game::w_terrain`, `w_overmap`, `w_minimap`, `ter_view_p`, `driving_view_offset` (`src/game.h:1272-1286`) |

Список конечный и короткий — следствие того, что CDDA рисует через один экран и один стек UI.

Статические локальные переменные в меню (запомненная позиция курсора, последний фильтр и
подобное) остаются общими между игроками. Это косметическая протечка, а не ошибка состояния;
принимается осознанно.

**Контекст существует в обеих сборках.** В одиночной игре он один, подмена — тождественная
операция, ровно как сейчас вектор слотов имеет размер один. Под флагом `MULTIPLAYER` остаются
только планировщик, сеть и серверный бэкенд curses. Это главный приём против гниения
мультиплеерного пути: подмена глобалов прогоняется всеми существующими тестами.

### 5.4 Планировщик

В каждый момент исполняется ровно один участник: либо контекст игрока, либо фаза мира. Право
исполняться — эстафета, передаваемая явно; настоящей параллельности нет.

Контекст игрока крутит внутренний цикл, унаследованный от hotseat: пока есть moves —
`handle_action()`, внутри которого управление уходит на ожидании ввода. Когда барьер по
правилу §7.2 выполнен, эстафета уходит фазе мира — существующему `do_turn()` с монстрами, NPC,
полями и календарём. Пока идёт фаза мира, ни один игрок не исполняется, поэтому мутация мира
остаётся строго последовательной, как в одиночной игре.

**Отдельного потока ввода-вывода нет.** Первая редакция этого спека закладывала его: поток,
не касающийся игрового состояния, наполняет очереди нажатий и сливает исходящие ячейки.
При проектировании Ф3a выяснилось, что он — механизм без задачи. `mp_transport::recv( timeout_ms )`
блокирующий и живёт на соединение, а поток игрока к моменту чтения эстафету уже отдал: он сам
себе поток ввода-вывода, пока не исполняется. Медленный сокет по-прежнему не тормозит симуляцию,
потому что держатель эстафеты в это время — кто-то другой.

Потоки появляются только с планировщиком, то есть с Ф3a. До него, пока игрок один, сервер
строго однопоточен: нарисовал, сбросил экран, заблокировался на приёме. Потоков в фазах Ф0
и Ф1 нет вовсе.

Уточнено в `2026-08-08-mp-phase3a-scheduler-design.md`, §6.1.

**Механизм: потоки со строгой эстафетой.** Поток на игрока, право исполняться передаётся через
мьютекс с условной переменной: отдал — немедленно заблокировался. Портабельный C++ без
ассемблера, у каждого игрока настоящий стек, отладчик показывает осмысленную картину. Режим
отказа при пропущенной точке переключения — зависание, то есть громкая и диагностируемая
ошибка, а не молчаливая порча состояния.

Альтернатива — фиберы (`ucontext`, Windows Fibers): параллельность невозможна по построению,
переключение дешевле, но требуется портабельная обвязка под три платформы, аккуратность с
исключениями через границу контекста, и хуже дружит с отладчиком и санитайзерами. При строгой
эстафете разница в гарантиях невелика, а в стоимости написания — существенна. Интерфейс
планировщика (`yield`/`resume`) прячет выбор, переход возможен локально.

**Сторожевой таймер.** Если эстафета удерживается одним контекстом дольше порога без единой
отдачи управления, это пишется в лог вместе с тем, кто её держит.

## 6. Протокол

### 6.1 Что передаётся

Сервер держит для каждого игрока композитный буфер экрана. Буфер сбрасывается в сокет **ровно
в момент, когда контекст этого игрока собирается заблокироваться на вводе** — то есть когда игра
закончила перерисовку и ждёт человека. Это даёт бесплатную дедупликацию: десяток перерисовок
внутри одного действия схлопывается в одну посылку, а игрок не видит промежуточных состояний.

Кадрирование — «длина плюс тело», четыре байта длины со старшего конца. Кодировка **гибридная**:
управляющие сообщения идут JSON через существующие `JsonOut` и `JsonValue`, потому что читаются
в логе глазами и не лежат на горячем пути; экран идёт компактным бинарём, потому что лежит.
Первый байт каждого тела — вид сообщения, он и разделяет два кодирования.

Экран передаётся **изменившимися строками, а не прямоугольниками**: гранулярность строки
совпадает с `cata_cursesport::curseline::touched`, то есть сервер отдаёт клиенту собственное
представление игры о том, что изменилось, ничего не пересчитывая. Внутри строки одинаковые
подряд идущие ячейки кодируются прогонами, поэтому пустой экран 80×24 — это сотни байт, а не
две тысячи. Полная перерисовка большого терминала — десятки килобайт, типовой ход — единицы.
Сжатие не закладывается: сначала измеряем на реальной игре, добавляем, только если худший
случай не влезает в бюджет.

Ячейка — глиф UTF-8 плюс два цвета, и цвета передаются **индексами в 256-цветном пространстве**.
Значения 0–15 приходят из `cata_cursesport::cursecell`, куда жирность и мерцание уже вложены
сдвигом на 8 (`src/cursesport.cpp:489-506`); 237 — `dark_gray`; значения выше 15 приходят от
imgui через imtui, который работает в ansi256. Раскрашивает клиент, своей палитрой.

### 6.2 Сообщения

Сервер клиенту: `hello_ack` (принят или отказ с причиной), `screen`, `cursor`,
`keyboard_mode`, `status` (кто держит барьер, идёт ли отсчёт), `bye`.

Клиент серверу: `hello` (версия, размер терминала, имя игрока, поддержка 256 цветов),
`input` (готовый `input_event`, включая мышь), `resize`, `bye`.

Клиент шлёт нажатия, **не дожидаясь ответа**; сервер копит их в очереди контекста. Печать вперёд
работает как в локальной игре — это главное, что делает игру при 30 мс RTT похожей на обычную.

### 6.3 Размер терминала

Каждый игрок получает экран своего размера: сервер выделяет контексту буфер по присланным
размерам, `resize` пересобирает окна этого контекста существующим путём обработки изменения
терминала. Требования CDDA к минимальному размеру проверяются при подключении, отказ — с
внятным сообщением.

### 6.4 Версионирование

Протокол версионируется с первого сообщения и допускает добавление новых типов потоков.
Несовпадение версии — отказ в подключении с внятным текстом.

**Содержимое игры и моды сверяются.** Пока клиент рисует присланные ячейки, они ему не нужны;
как только он рисует сам — а целевая сборка на тайлах, см. §13 — ему нужны совпадающие
идентификаторы предметов, монстров и террейна для тайлсета и совпадающие JSON-определения
виджетов для сайдбара. Расхождение даёт не отказ в отрисовке, а тихо неверную картинку,
поэтому сверка идёт при подключении, а несовпадение — отказ с внятным текстом.
Решено в `2026-08-06-mp-phase2-context-design.md`, §10.

### 6.5 Транспорт

Свои BSD-сокеты с тонким шимом под Winsock. Новых зависимостей не появляется: ни SDL_net
(сервер получил бы зависимость от SDL, а поддерживать пришлось бы обе ветки — `SDL2_net` и
`SDL3_net`), ни asio (сотни заголовков в дереве и ещё одна точка конфликта при каждом
вливании апстрима). Для задачи «один слушающий сокет, N клиентских, кадры длина плюс тело»
асинхронная машинерия избыточна.

**`TCP_NODELAY` обязателен на обоих концах.** Без него алгоритм Нейгла склеит мелкие пакеты и
добавит десятки миллисекунд ровно на пути «нажатие → экран», то есть на единственном пути,
от которого зависит ощущение игры. Это не оптимизация, а условие работоспособности.

Сокеты неблокирующие, частичные чтения собираются кадровым сборщиком, частичные записи
копятся в исходящем буфере и дописываются при следующей возможности. `EINTR` не ошибка,
`SIGPIPE` подавляется. Тестируется всё это на настоящих сокетах через 127.0.0.1, а логика
поверх транспорта — на реализации в памяти с инжекцией задержки.

## 7. Модель хода

### 7.1 Состояния игрока

Выводятся из состояния, а не хранятся отдельно:

- *действует* — есть moves, контекст исполняется;
- *отходил* — moves потрачены, **либо** запущена активность, **либо** назначена дальняя цель
  движения: и то и другое израсходует этот ход без единого нажатия, так что игрок уже сказал
  игре, что делает, и ждать его незачем;
- *держит* — moves есть, контекст стоит на ожидании ввода (думает или сидит в меню);
- *не ждём* — объявил, что выпал, либо был автопропущен, либо потерял связь.

Второе и третье условия *отходил* добавлены в Ф3a и они принципиальны, а не оптимизация: ход
в CDDA — типично одно действие, а листание меню времени не тратит, поэтому без них любое чужое
открытое меню — это ваша пауза. Они же — дешёвая замена «фазе планирования ходов», которая
рассматривалась и отложена (`2026-08-08-mp-phase3a-scheduler-design.md`, §10).

### 7.2 Барьер

Мир тикает, когда каждый живой игрок либо *отходил*, либо *не ждём*.

### 7.3 Ленивый таймаут

Реализуется в **Ф3a вместе с барьером**, а не в Ф4, как планировалось изначально. Причина
арифметическая: ход в CDDA — типично одно действие (аватар получает ~100 moves за тик, шаг
стоит ~100), а листание меню времени не тратит, поэтому игрок, открывший инвентарь, остаётся
*держит* и морозит партнёра на всё время чтения. Голый барьер §7.2 без механизма снятия делает
вечер вдвоём непроходимым — а это как раз ворота Ф3a. Решено
в `2026-08-08-mp-phase3a-scheduler-design.md`, §7.

Там же добавлено второе условие состояния *отходил*, которого здесь не было: игрок с запущенной
активностью или назначенной дальней целью движения считается отходившим. Он сказал игре, что
делает, и ждать его незачем.

Игрок, который уже отходил и упёрся в барьер, может нажать «тороплю». Это запускает видимый
обратный отсчёт у всех, кто *держит*. По истечении сервер **не лезет в чужой UI и ничего не
закрывает** — он снимает с этого игрока обязанность держать барьер на этот тик. Персонаж стоит
и получает по морде, меню остаётся открытым, игрок дочитывает список рецептов и подтверждает
выбор, когда ему удобно.

Цена: выбранное может к тому моменту протухнуть (предмет унесли, станок сломали). Игра ответит
обычным сообщением об отказе, как отвечает и в одиночной игре. Принимается явно.

Пока в бабле есть враждебное существо, которое кого-то из игроков видит, отсчёт запускается
автоматически и он короче. Никто не тратит нажатие на «тороплю», когда на него бегут.

### 7.4 «Ходите без меня»

Тот же механизм, объявленный явно и залипающий до возвращения игрока. Закрывает «отошёл за
чаем» без кика и без остановки сессии. Обрыв связи к этому состоянию не приводит: в текущей
редакции он завершает сессию для всех (см. `doc/MULTIPLAYER.md`, «Limitations of this first
version»).

Возвращает игрока **действие, тратящее ход**, а не любое нажатие. Свободное действие
(инвентарь, карта, просмотр, сообщения и остальное из `mp_action_is_free()`) оставляет его
ушёдшим, иначе чтение меню вернуло бы игрока в барьер — ровно тот дефект, из-за которого
`mp_turn_reset()` не трогает флаги ввода (`src/mp/mp_turn.h:108-132`). Вернуться можно и
повторным нажатием `:`.

Ушедший не копит ходы: они сжигаются каждый ход, как у drop, поэтому возвращение не даёт
запаса на десятки действий. Сервер за него не играет, меню ему не закрывает и сам не
возвращает.

Если ушли все живые игроки, ход остаётся открытым, а мир стоит: тикать вокруг пустых стульев
некому. Выход — вернуться.

Бой не даёт разогнаться мимо ушедшего: пока враждебное существо кого-то видит и никто не
играет руками, ход закрывается не быстрее боевого отсчёта (§7.3), а не со скоростью CPU.

Все состояния видны всем: в боковой панели строка «ждём: игрок X» и отсчёт, если он идёт, и
добавка «away: Y» для ушедших. Место для этого есть — hotseat добавил туда виджет активного
слота.

### 7.5 Долгие активности

Свободный прогон уже реализован резюмируемым ходом в Ф3a: мир тикает, пока у каждого живого
игрока запущена активность или назначена дальняя цель движения (`acted`), и
останавливается на ближайшем тике, где кто-то снова держит барьер. Сон до утра проходит за
секунды; договариваться не нужно — сам факт, что все легли спать, и есть согласие.
Доказательство — тест `two_busy_players_do_not_hold_the_world`.

Ф4 добавляет к этому два ограничения. Прогон не разгоняет бой: пока враждебное существо
кого-то видит, ход длится не меньше боевого отсчёта. И прогон не включается, когда ушли все
живые игроки (§7.4): пустая сессия стоит, а не перематывает мир.

### 7.6 Пространство

Тезер и якорь бабла работают как в hotseat и по тем же причинам: бабл 132×132 тайла,
края симулируются некорректно, безопасный радиус от якоря 42 тайла, мягкий предел 32.
Это ограничение движка, а не сети.

## 8. Жизненный цикл

### 8.1 Мир и сейвы

Мир принадлежит серверу: обычная директория мира CDDA, **по файлу сейва на персонажа** —
ровно как в ванильном мире с несколькими персонажами. Автосейв идёт по существующей настройке
`AUTOSAVE_TURNS` и всегда попадает в фазу мира, когда эстафета у сервера и ни один игрок не
исполняется; сохраниться посреди чужого действия физически невозможно. Сохранение N персонажей —
цикл «активировать контекст игрока → сохранить», поверх механизма подмены из Ф2.

Первая редакция этого спека описывала другую модель: несколько аватаров **внутри** сейва слота 0,
массивом `extra_players`, как это сделал MVP-2. Она отменена в Ф3b. Причина в том, что обещание
следующего абзаца при ней было половинчатым: слот 0 вынуть можно, а напарник заперт внутри чужого
файла и в одиночку не играется никогда. Решено
в `2026-08-08-mp-phase3b-join-design.md`, §4.

**Отдельный тип мира не вводится.** Требование старого спека (§5.1) существовало затем, чтобы
одиночный сейв не попал в lockstep-конвейер. Конвейера нет: кооперативный мир — обычный мир,
в котором персонажей больше одного. Следствие обоюдное и теперь полное в обе стороны: любой
существующий одиночный сейв можно отдать серверу и позвать друга, а любого персонажа
кооперативного мира можно открыть локально и играть в одиночку.

### 8.2 Вход

Реализуется в **Ф3b**, а не в Ф5, и в форме меню на каждом клиенте, а не автоматического поиска
по имени.

Мир грузит сервер (`--world`), после чего каждый клиент получает **своё** меню входа в своём
контексте: создать персонажа (custom, preset, random) или продолжить за своего. Отдельного кода
создания персонажа не нужно — это такой же UI, как любое меню, и он исполняется в контексте
своего игрока, как обещала первая редакция.

Клиент опознаёт себя **карточкой персонажа** — жетоном из адреса сервера, имени мира, `save_id`
и имени, который он держит в своей userdir. Сейва персонажа клиент не держит: без мира он
неиграбелен. Сервер авторитетен всегда; карточка, указывающая на несуществующего персонажа,
вырождается в предложение создать нового.

Партия начинается, когда все выбрали. Готовые видят экран ожидания. Новые персонажи появляются
вплотную к группе, а не по стартовой локации сценария: бабл один, и тезер (§7.6) иначе нарушается
до первого хода. Решено в `2026-08-08-mp-phase3b-join-design.md`, §6-§9.

### 8.3 Выход

Обрыв не завершает сессию. Слот становится `disconnected`: avatar остаётся в мире обычным
живым телом без AI, барьер его не ждёт, ходы сжигаются; тезер его учитывает, монстры могут
его убить. Возврат — в тот же avatar. Льготного интервала и NPC-handoff в Ф5 нет: это
отклонение от прежней редакции, записано в ADR `0001-disconnected-avatars-stay-in-the-world`.
Добровольный выход обрабатывается так же, как сетевой обрыв.

### 8.4 Смерть

Смерть не завершает сессию. Труп остаётся на месте; подключённый игрок получает всплывающее
меню создания персонажа (как при подключении), замена появляется рядом с группой через
`place_new_character()`. Наблюдателя нет. Сессия заканчивается только когда не осталось
подключённых клиентов; смерть всех персонажей при живых клиентах — не конец.
ADR `0002-death-does-not-end-the-session`.

### 8.5 Конфигурация сервера

Порт, мир, число игроков и длины отсчётов задаются командной строкой и JSON-файлом
`<userdir>/config/mp/server.json`; приоритет CLI > файл > значения по умолчанию. Ключи:
`port`, `world`, `players`, `hurry-ms`, `hurry-combat-ms`. Битый JSON, неизвестный ключ или
значение не того типа — отказ стартовать с сообщением оператору. Значение `hurry-*` вне
`[1000, 600000]` обрабатывается как у флагов: отказ, запись в лог, работа на значениях по
умолчанию. Файл читает те же сеттеры (`mp_set_hurry_lengths()`), второго пути нет. Льготный
интервал до NPC в Ф5 не вводится.

### 8.6 Безопасность

Вне скоупа: доверенный круг, LAN или VPN-оверлей, ни аутентификации, ни шифрования.

Одно ограничение старого спека при этом исчезает бесплатно: §11 признавал, что серверного тумана
войны нет, потому что клиент держит весь бабл в памяти. Теперь клиент не держит ничего — он
получает нарисованные ячейки. Туман войны стал настоящим, и модифицированный клиент не увидит
того, чего сервер ему не нарисовал.

## 9. Отказы

**Обрыв связи.** Игрок снимается с барьера, сессия продолжается. Через льготный интервал персонаж
переводится в follower-npc, как при штатном выходе. Переподключение — полная перерисовка экрана
и продолжение с того места, где человек был.

Тонкое место: контекст отвалившегося может стоять глубоко в меню, а поток, зависший внутри чужого
UI, нельзя просто убить. Решение по средствам самой игры — сервер подаёт в его очередь ввода
отмену (`ESC`) столько раз, сколько нужно, чтобы контекст сам вернулся на верхний уровень, и
только там разбирает его. Если за разумное число попыток не вернулся, контекст паркуется до конца
сессии, а персонаж остаётся под AI; событие громко логируется, но сессию не роняет.

**Падение сервера.** Мир теряется до последнего автосейва, как в одиночной игре при падении.
Клиенты видят разрыв и выходят.

**Зависший контекст.** Сторожевой таймер планировщика (§5.4). Единственный режим отказа
планировщика, и он диагностируемый.

**`debugmsg` на сервере не имеет права быть модальным.** В одиночной игре ошибка открывает окно
и ждёт нажатия. На сервере она может сработать в фазе мира, когда ни один контекст игрока не
активен и показывать окно физически некуда, — это мгновенный тупик сессии. В серверной сборке
`debugmsg` пишет в лог и рассылает строку в сообщения всем игрокам, но никогда не блокирует.

**Медленный клиент.** Исходящая очередь растёт — сервер схлопывает накопившиеся дельты в одну
полную перерисовку и шлёт её вместо истории. Экран идемпотентен, терять промежуточные кадры
безопасно.

**Долгие неинтерактивные операции** (генерация карты при сдвиге бабла, загрузка) держат эстафету
и подмораживают всех на те же миллисекунды, на которые подмораживают одиночного игрока.
Принимается как есть.

## 10. Тестирование

Десинков больше нет, поэтому вся диагностика старого спека вокруг них не нужна. Взамен появляются
три хрупких места, и тесты бьют в них.

**Полнота контекста — главный класс ошибок этого дизайна.** Забытый глобал проявится как «игрок 1
видит меню игрока 2» или как действие, выполненное не тем персонажем. Тест: сценарий открывает
разные меню у двух игроков, чередует их нажатия и сверяет буфер экрана каждого с эталоном того же
меню, снятым в одиночной сессии. Протёкший глобал меняет картинку и виден сразу. Список тяжёлых
меню: инвентарь, крафт, карта, лист персонажа, транспорт, строительство.

**Строгость эстафеты.** Прогон сессионного харнесса под ThreadSanitizer. Поскольку в каждый момент
исполняется ровно один контекст, TSAN обязан молчать; любое срабатывание — настоящая пропущенная
передача управления. Дешёвые и решающие ворота в CI.

**Протокол экрана.** Property-тест: случайные последовательности отрисовок окон, применение дельт
на стороне клиента, сверка клиентского буфера с серверным композитом; отдельно — схлопывание
в полную перерисовку при переполнении очереди.

**Сессионный харнесс** — рабочая лошадка: сервер и N клиентов в одном процессе на loopback-
транспорте, скриптованные потоки нажатий, проверки и по состоянию мира, и по экранам. На нём же
гоняются жизненный цикл (вход, выход в npc, возврат, обрыв посреди меню с раскруткой через `ESC`,
смерть и новый персонаж, автосейв в фазе мира) и барьер (ленивый таймаут, «тороплю», «ходите без
меня», автоторопление в бою, разгон на долгих активностях и его прерывание). В транспорт
закладывается искусственная задержка — иначе неизбежно напишется код, работающий только при
нулевом RTT.

**Регресс одиночной игры** — 266 тестовых файлов зелёные. Главный критерий того, что рефактор
контекстов ничего не сломал.

Проба детерминизма из MVP-0 остаётся в дереве как дешёвая проверка вменяемости, но перестаёт быть
несущей.

## 11. План по фазам

Порядок выбран так, чтобы самое дешёвое доказательство самого спорного места шло первым. Спорное
здесь не планировщик, а вопрос «играбельна ли игра через стриминг экрана», и он проверяется
на одном игроке, без всякой многопользовательности.

| Фаза | Содержание | Критерий готовности | Недель |
|---|---|---|---|
| Ф0 | Серверный бэкенд curses: headless-цель, линкующая `cursesport`, `curses_drawwindow()` в композитный буфер, `get_input_event()` из очереди, выкладка кадров imgui через imtui. Loopback | Один игрок играет полноценную игру «через провод» в одном процессе, включая imgui-экраны (крафт, инвентарь) | 3–4 |
| Ф1 | TCP-транспорт и клиент `--connect`, `hello`/`resize` | **Ворота:** вечер обычной одиночной игры по сети с другой машины | 1–2 |
| Ф2 | Контекст игрока: глобалы в структуру, один контекст в обеих сборках | 266 тестов зелёные, эталонные снимки экранов совпадают | 2–4 |
| Ф3a | Снос цикла hotseat, разрез `do_turn`, планировщик с эстафетой, барьер с «тороплю», объекты на сессию, мультиклиентский сервер | **Ворота человека:** вечер игры вдвоём по TCP с двух машин. **Ворота CI:** два игрока в разных меню на loopback, TSAN молчит, весь набор зелёный | 4–5 |
| Ф3b | Вход в сессию: мир грузит сервер, меню входа на каждом клиенте, создание персонажа, сейв на персонажа, размещение вокруг опорного | Двое подключаются к голому миру, каждый создаёт персонажа с нуля, партия идёт; второй прогон — оба продолжают за своих | 2–3 |
| Ф4 | Залипающее «ходите без меня», разгон долгих активностей, настройка длительностей отсчётов, `status`-сообщение | Сон до утра за секунды; AFK не морозит сессию | 1–2 |
| Ф5 | Остаток жизненного цикла: вход и выход посреди партии, обрыв и возврат, смерть и замена, конфиг-файл сервера | Сессия переживает обрыв и смерть одного игрока; новый клиент занимает слот «мёртв + отключён» | 2–3 |
| Ф6 | Тезер и якорь под N игроков (в основном есть из MVP-2) | Трое расходятся до предела, бабл держит | 1 |
| Ф7 | Продолжение sim-рефактора: остатки `get_avatar()` в симуляции | Монстры и NPC одинаково реагируют на всех игроков | 2–4 |
| Ф8 | Полировка, отладка на живой игре, диагностика | Играбельно | 3–6 |

Итого 20–33 недели против 30–47 у старого спека.

**Ф3 разделена надвое** при брейншторме 2026-08-08. Деление по живому шву: Ф3a доказывает
спорную и новую механику, Ф3b делает её пригодной для человека без дебаг-меню. Порядок — по тому
же правилу, что и вся лестница: самое рискованное измеряется первым и дёшево.

Заодно перераспределены две вещи. **Ленивый таймаут переехал из Ф4 в Ф3a** (§7.3): без механизма
снятия с барьера ворота Ф3a не проходятся. **Вход и создание персонажа переехали из Ф5 в Ф3b**
(§8.2): без них до ворот Ф3b не добраться. В Ф4 остаётся то, что действительно отдельно,
и она сократилась.

Спеки: `2026-08-08-mp-phase3a-scheduler-design.md`, `2026-08-08-mp-phase3b-join-design.md`.

**Ворота после Ф1.** Если игра по сети ощущается плохо — задержка в меню, артефакты отрисовки,
неудобная печать вперёд, — модель тонкого клиента пересматривается до того, как в планировщик
и контексты вложены недели. Это прямой аналог лестницы MVP старого спека: смертельный риск
измеряется первым и дёшево.

Каждая фаза планируется отдельно.

## 12. Риски

1. **Пропущенный глобал в контексте.** Самый вероятный класс ошибок. Смягчается эталонными
   снимками экранов (§10) и тем, что список глобалов короткий и известен (§5.3).
2. **Протухший выбор.** Игрок думал минуту, мир ушёл вперёд, выбранный предмет исчез. Не ошибка,
   а свойство модели; игра отвечает обычным отказом. Принимается явно.
3. **Раскрутка чужого стека при обрыве.** Подача `ESC` — приём по средствам игры, но не
   гарантирует возврата из любого меню. Запасной путь — парковка контекста, сессия жива.
4. **Блокирующие операции сервера морозят всех.** Тот же порядок величин, что заикание
   в одиночной игре.
5. **Гниение мультиплеерного пути.** Смягчается тем, что контекст живёт в обеих сборках (§5.3),
   и сессионным харнессом в CI с первой фазы.
6. **Конфликты при вливании из апстрима.** Существенно меньше, чем в старом дизайне: 2628 мест
   с UI не трогаются вообще, слоя намерений нет. Диффы в существующих файлах ограничены пятью
   местами: условие `TUI` в `src/cursesport.h`, guard в `src/ncurses_def.cpp`, развилка выбора
   бэкенда imgui в `src/cata_imgui.cpp`, аргументы командной строки в `src/main.cpp`, система
   сборки. Плюс структура контекста и `game.h` начиная с Ф2.

   Начиная с Ф3a список расширяется на два содержательных места, и это осознанная цена решения
   «один путь для обоих билдов»: **`src/do_turn.cpp`** (разрез хода) и **`src/game_io.cpp`**
   (разрез загрузки и сохранения, Ф3b). Альтернативой была гниющая мультиплеерная ветка,
   не прогоняемая обычными тестами, — риск §12.5. Вместе с `src/cata_imgui.cpp` это три файла,
   за которыми надо следить при вливаниях.
7. **Несколько персонажей в одном мире — путь, который апстрим сам считает шатким.**
   `src/main_menu.cpp:983` при создании второго персонажа в мире предупреждает: «Many game
   features will not work correctly with multiple characters in the same world». Весь дизайн
   стоит ровно на этом пути. MVP-2 доказал, что игра не разваливается, но списка «что именно
   не работает» не составлял никто, включая апстрим. Ф3b составляет его отдельной задачей
   с воротами — это единственная задача проекта с открытым исходом, и она способна изменить
   границы поздних фаз.

## 13. Известные ограничения

- **Клавиатурные раскладки живут на сервере.** Клиент шлёт сырые нажатия, в действия их
  превращает `input_context` на сервере. В первой версии все играют с раскладкой сервера.
  Персональные профили ложатся естественно (`inp_mngr` уже в контексте игрока), но это отдельная
  работа.
- **Звука у клиентов нет.** Сервер headless, `sfx` не работает. Сообщения «сыграй звук X» —
  расширение протокола, вне первого этапа.
- **TILES для сетевой игры появляются не сразу.** До tiles-фазы клиент в TILES-сборке
  работает, но рисует присланные ячейки шрифтом; графических тайлов карты нет. Тайлы —
  целевой режим, а не отложенная возможность: поток описания вьюпорта («дверь, которую
  оставляем открытой» ниже) реализуется, вместе с ним сайдбар переходит на передачу значений
  виджетов вместо ячеек. Цена — сверка контента и модов при подключении (§6.4).
  Решено в `2026-08-06-mp-phase2-context-design.md`, §6.5 и §10.
- **Статические локальные переменные меню общие** между игроками — косметическая протечка.
- **Клиент бесполезен без сервера.** Это цена тонкого клиента и она принимается. Одно уточнение
  с Ф3b: клиент держит у себя **карточку персонажа** — адрес сервера, имя мира, `save_id` и имя, —
  чтобы при следующем подключении опознать себя и предложить «продолжить за своего». Играть
  по карточке нельзя, сейва персонажа клиент не хранит: без мира тот неиграбелен. Принцип в силе,
  сервер остаётся единственным источником правды. Решено
  в `2026-08-08-mp-phase3b-join-design.md`, §7.

**Дверь, которую оставляем открытой.** Протокол версионируется с первого сообщения и допускает
добавление новых типов потоков. Это ровно то, что понадобится для TILES-клиента (поток описания
вьюпорта вместо ячеек) и, потенциально, для free-roam: при одной авторитетной симуляции разные
баблы у разных игроков перестают быть архитектурно невозможными и становятся вопросом того, что
именно сервер стримит. Ни то, ни другое в скоуп не входит.
