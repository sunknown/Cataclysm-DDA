# Кооперативный мультиплеер для Cataclysm-DDA — дизайн

Дата: 2026-07-31
Статус: утверждён к планированию

## 1. Контекст и цель

Cataclysm-DDA — пошаговый рогалик на 773 тысячи строк C++ (929 файлов в `src/`), спроектированный вокруг единственного игрока. Апстрим отказался от мультиплеера явно и окончательно (`doc/FREQUENTLY_MADE_SUGGESTIONS.md:128`), поэтому работа ведётся в форке и не рассчитывает попасть в upstream.

Цель: кооперативная игра на 2–4 игроков в одном мире с сохранением пошаговой сути игры и без деградации одиночного режима.

## 2. Скоуп

### В скоупе

- Tethered-кооп: игроки обязаны оставаться в пределах одного reality bubble.
- Выделенный сервер-арбитр, клиенты гоняют полную симуляцию, по сети идут намерения игроков.
- Буферизация намерений с барьером и таймаутом.
- Ускорение времени для долгих активностей (сон, крафт) с явным голосованием.
- Мультиплеер как **полностью отдельный режим**: отдельный флаг сборки, отдельный игровой цикл, отдельный тип мира.

### Вне скоупа

- Free-roam (игроки в разных баблах). Требует стриминга состояния мира — см. §11.
- PvP.
- Шифрование, аутентификация, защита от модифицированного клиента, обход NAT.
- Матчмейкинг, лобби, серверный браузер.
- Кроссверсийная и кроссмодовая совместимость клиентов.

## 3. Сводка принятых решений

| Решение | Выбор |
|---|---|
| Топология | Выделенный сервер-арбитр, N клиентов |
| Формат провода | Намерения игроков, не состояние мира |
| Модель симуляции | Lockstep: сервер и все клиенты гоняют идентичную полную симуляцию |
| Пространство | Tethered — все игроки в одном бабле |
| Представление игрока | Полноценный второй `avatar`, не npc |
| Модель хода | Буфер намерений + барьер, с таймаутом в бою |
| Долгие активности | Автоускорение батчами + явное голосование за скип |
| Политика меню | Вне боя барьер бесконечен, в бою таймаут |
| Изоляция режимов | Флаг сборки, отдельный цикл, отдельный тип мира |
| Sim-рефактор | Поэтапно: боевое ядро сразу, остальное под лит-гардом |

## 4. Анализ существующей архитектуры

Находки, на которых стоит дизайн.

### Препятствия

- **Reality bubble.** `MAPSIZE = 11` сабмапов (`src/map_scale_constants.h:11`), `SEEX = 12`, 21 z-уровень (`OVERMAP_DEPTH = 10`, `OVERMAP_HEIGHT = 10`). Бабл — 2541 сабмап, ≈366 тысяч тайлов. Вне бабла мир не симулируется. Это делает free-roam невозможным без переписывания ядра.
- **Синглтон игрока.** `get_avatar()` — 560 вызовов, `get_player_character()` — 758, `g->` — 1264. В симуляционно-критичных файлах: `game.cpp` 38, `npcmove.cpp` 30, `monattack.cpp` 29, `map.cpp` 28, `monster.cpp` 18, `npc.cpp` 16, `monmove.cpp` 10.
- **Ввод внутри цикла хода.** `game::do_turn()` (`src/do_turn.cpp:522`) содержит `while( u.get_moves() > 0 )` (`:633`), внутри которого `handle_action()` блокируется на клавиатуре. `game::handle_action()` — 3488 строк (`src/handle_action.cpp:3252`), где чтение ввода, вложенные меню и мутация мира перемешаны.
- **Порядок итерации.** `creature_tracker.h:150` — `std::unordered_map<tripoint_abs_ms, shared_ptr_fast<monster>> monsters_by_location`; `:164` — вложенный `unordered_map` по фракциям. Порядок обхода не воспроизводим между процессами.
- **Апстрим враждебен.** Вливания будут конфликтовать бессрочно.

### Опоры

- **`activity_actor`** (`src/activity_actor.h:145`) — иерархия из 94 сериализуемых классов действий с реестром десериализаторов. Готовый тип «полностью разрешённое намерение».
- **`item_location`** сериализуется (`src/item_location.h:53`) — стабильная ссылка на предмет, пригодная к передаче.
- **`avatar` тонкий** — 504 строки заголовка поверх `Character` (4374). Разсинглтонить реально.
- **`game::update_map( int &x, int &y, bool )`** (`src/game.h:704`) уже принимает координаты, а не аватара. Центрирование бабла на произвольной точке почти бесплатно.
- **`game::vertical_shift`** (`src/game.cpp:10132`) отдельно двигает `u` и отдельно зовёт `map::vertical_shift(z)` — шов для расцепления чистый.
- **`avatar::control_npc`** (`src/avatar.cpp:154`) — готовая механика передачи управления между персонажем игрока и follower-npc, включая перевод миссий и смену фракции.
- **Симуляция однопоточная.** `std::thread`/`std::async`/OpenMP встречаются только в `src/sounds.cpp` и `src/mingw.thread.h`. Гонок в сим-коде нет по построению.
- **Headless-сборка есть** (`TILES=0`), 266 тестовых файлов линкуют игровой код без UI.
- **Кастомные clang-tidy-чеки** уже существуют в проекте (например `cata-serialize`) — инфраструктура для лит-гардов готова.

## 5. Архитектура

### 5.1 Изоляция режимов

Три уровня.

**Сборка.** Весь мультиплеерный код живёт в `src/mp/` и компилируется только при `MULTIPLAYER=1` (Makefile) или соответствующей опции CMake. Дефолтный одиночный билд не содержит его вообще. Сервер собирается как отдельная цель `cataclysm-server` без SDL и curses.

**Рантайм.** `game::do_turn()` для одиночной игры не изменяется. Мультиплеер получает собственный `mp_game_loop`. Развилка единственная и находится в точке входа, при выборе режима из главного меню. Проверки вида `if( is_multiplayer() )`, рассыпанные по игровому коду, запрещены.

**Данные.** Мультиплеерный мир помечается флагом в `worldfactory`. Одиночный сейв нельзя открыть как мультиплеерный и наоборот.

### 5.2 Слой `src/mp/`

| Модуль | Ответственность |
|---|---|
| `mp_session` | Роль (`server` / `client`), список пиров, хендшейк, сверка версии и модов |
| `mp_transport` | TCP-транспорт плюс loopback-реализация для тестов |
| `mp_intent` | Сериализуемое намерение игрока |
| `mp_turn_sync` | Буферы намерений, барьер, детерминированный порядок исполнения |
| `mp_batch` | Ускорение времени, точки синхронизации, голосование за скип |
| `mp_desync` | Хеш состояния, детект расхождения, resync через пересылку сейва |
| `mp_game_loop` | Мультиплеерный цикл хода |

### 5.3 Модель намерения: разделение выбора и исполнения

Центральный инвариант дизайна:

> **`apply_intent` не имеет права открыть ни одно окно и ни о чём спросить игрока.**

Всё, что требует решения игрока, принимается в фазе выбора и полностью записывается в `mp_intent`.

```
фаза ВЫБОР — локально, мир не мутирует, по сети не идёт
    клавиша -> action_id -> вложенные меню -> все выборы сделаны
        v
    mp_intent { act, item_location..., tripoint..., activity_actor }
        v
фаза ИСПОЛНЕНИЕ — идентично на сервере и всех клиентах, ноль UI
    apply_intent( slot.av, intent )
```

`activity_actor` и `item_location` покрывают этот контракт для 94 действий без дополнительной работы. Остальные намерения (движение, ближняя атака, стрельба, ожидание, отмена) — простые структуры на два-три поля.

Общим между режимами остаётся только исполнение:

```cpp
// одиночная игра — текстово почти не меняется
handle_action()
    intent = choose( ... );          // ввод и все вложенные меню
    apply_intent( u, intent );       // исполнение немедленно

// только в мультиплеерной сборке
mp_handle_action()
    intent = choose( ... );          // тот же choose
    send( intent ); buffer( intent );
    // позже, по барьеру:
    apply_intent( slot.av, intent );
```

Одна реализация `choose`, одна `apply_intent`. Дублирование `handle_action` и слоя действий недопустимо — оно даст две расходящиеся игры.

Критерий корректности этого рефактора: 266 существующих тестовых файлов зелёные, наблюдаемое поведение одиночной игры не изменилось.

### 5.4 Слот игрока и второй `avatar`

`avatar` перестаёт быть синглтоном.

```cpp
struct player_slot {
    avatar                 av;        // полноценный avatar, не npc
    std::deque<mp_intent>  buffer;    // буферизованные намерения
    peer_id                owner;
    int                    acked_turn;
};
```

`game` держит `std::vector<player_slot> players` и индекс `local_slot`. Эта структура живёт в `game`, а не в `src/mp/`, и присутствует в обеих сборках: **в одиночной игре вектор всегда размера 1**, `local_slot` равен нулю, поля `buffer`, `owner` и `acked_turn` не используются. Наблюдаемое поведение одиночной игры не меняется — меняется только форма хранения.

`get_avatar()` сохраняется и возвращает локальный слот. Все 73 файла, принимающие `avatar &` (`avatar_action.cpp`, `game_inventory.cpp`, `crafting.cpp`, `bionics.cpp`, `construction.cpp`, `butchery.cpp` и прочие), не изменяются — для них локальный игрок и есть «тот самый».

Вводятся новые точки доступа для симуляционного кода:

- `game::get_players()` — все живые игроки в стабильном порядке;
- `game::nearest_player( tripoint )` — ближайший игрок к точке;
- `game::any_player_sees( tripoint )`.

Второй игрок — именно `avatar`, а не управляемый npc. Вариант с npc отвергнут: для него не работал бы весь слой игровых действий, принимающий `avatar &`, и второй игрок стал бы неполноценным.

### 5.5 Мультиплеерный цикл хода

```
mp_game_loop():
    while( any_player_has_moves() ):
        if !turn_sync.ready():
            pump_network(); render(); continue
        for slot in players:                       // фиксированный порядок по индексу слота
            while slot.av.moves > 0 and slot.buffer.nonempty():
                apply_intent( slot.av, slot.buffer.pop_front() )
    monmove()                                       // монстры и NPC как в одиночной игре
    calendar::turn += 1_turns
```

Порядок игроков — по индексу слота, не по скорости и не по времени прихода пакета. Детерминированно.

Действия игроков исполняются в рамках одного тика, последовательно в фиксированном порядке. Это и есть «одновременность» с точки зрения игроков.

### 5.6 Барьер и таймаут

`turn_sync.ready()` истинно, когда у каждого слота есть хотя бы одно намерение на текущий тик.

- **Вне боя** барьер бесконечен. Мир ждёт сколько угодно — можно спокойно разбирать рюкзак.
- **В бою** действует таймаут 3 секунды.
- Переход в бой выкидывает игрока из открытого меню с предупреждением.

Критическое правило:

> **Таймаут решает владелец слота, а не наблюдатель.**

Когда у игрока истекает локальный таймер, он **сам** отправляет `intent::wait` как обычное намерение. Ни сервер, ни другие клиенты никогда не додумывают действие за отсутствующего. Это полностью убирает влияние локальных часов на симуляцию и вместе с ним — целый класс десинков.

`combat_mode = any_player_sees_hostile()` — детерминированная функция состояния мира, но используется только для длины локального таймера. Даже расхождение пиров в этой оценке не приводит к десинку.

Отвал пира — не таймаут хода. Отсутствие пакетов дольше порога соединения останавливает игру и показывает диалог, а не продолжает симуляцию.

### 5.7 Anchor бабла и тезер

Anchor бабла — **целочисленная середина между игроками в координатах сабмапов**, округление вниз, без арифметики с плавающей точкой. Вычисляется всеми одинаково.

`game::update_map( int &x, int &y, bool )` уже принимает координаты, поэтому центрирование не требует нового API.

Anchor по z — z-уровень слота 0. `game::vertical_shift` расцепляется на «сдвинуть бабл по z» и «переместить персонажа». Бабл держит все 21 уровень, поэтому игроки на разных этажах проблемы не создают.

**Тезер.** Бабл — 132×132 тайла, то есть ±66 от anchor. Края симулируются некорректно: монстры и поля за границей отсутствуют, обзор обрывается. С запасом в 24 тайла безопасный радиус от anchor равен 42.

- 32 тайла от anchor — мягкий предел: предупреждение и указатель направления к напарнику.
- 42 тайла от anchor — жёсткий предел: шаг наружу запрещён с сообщением.

Максимальное расстояние между двумя игроками — 84 тайла, когда оба стоят на противоположных жёстких пределах.

### 5.8 Долгие активности

Сон — 8 часов, то есть 28800 тиков. Крафт — до 14400. В одиночной игре это фаст-форвард, в кооперативе так нельзя.

**Автоускорение.** Когда все слоты находятся в долгой активности и `combat_mode == false`, сервер объявляет `batch( N = 100 )`. Все участники крутят 100 тиков локально, без сетевого обмена и без отрисовки. Между батчами — точка синхронизации: обмен хешем и применение накопившихся прерываний.

Детерминированные прерывания (урон, звук, появление видимого врага, завершение активности) останавливают батч на одном и том же тике у всех, потому что являются функцией состояния мира.

Локальное нажатие ESC асинхронно, поэтому не прерывает мгновенно: оно превращается в намерение `abort` и применяется на ближайшей точке синхронизации. Задержка не более 100 тиков, около 10 секунд игрового времени.

**Голосование за скип.** Намерение `propose_skip( until )`, подтверждение `accept_skip` от остальных, после чего сервер объявляет длинный батч с целью «до заданного времени или до первого прерывания». Любой участник может прервать.

## 6. Сеть

### 6.1 Транспорт и хендшейк

TCP, кадры «длина плюс тело». Объём трафика — десятки байт на ход; пропускная способность и задержка не критичны, а порядок и надёжность даёт сам TCP. UDP не нужен.

Формат сообщений — JSON через существующие `JsonOut` и `JsonValue`. Проект целиком построен на них, `activity_actor` и `item_location` уже умеют сериализоваться, а читаемость сообщений глазами существенно ускоряет отладку десинков.

Хендшейк отклоняет соединение при несовпадении любого из: версия протокола, git-хеш билда, хеш загруженного JSON-контента (набор модов). После успешной сверки сервер передаёт сид RNG, номер стартового хода и полный сейв мира.

### 6.2 Роли и процессы

`session_role = { server, client }`.

Сервер — отдельный процесс, гоняющий ту же симуляцию headless. Он авторитетен в следующем:

- единственный источник порядка — штампует номера ходов и последовательность намерений;
- единственный источник истины — при расхождении хешей его состояние каноническое;
- валидатор — отклоняет невозможные намерения (нет предмета, не хватает moves, цель вне досягаемости);
- владелец RNG — задаёт сид, поток общий;
- держит мир без игроков, что позволяет постоянно работающий выделенный сервер.

Клиенты — полные симуляции, но истину не определяют.

### 6.3 Сейвы, вход и выход

- Мир живёт на сервере. Клиент получает его при входе, держит в памяти, собственным сейвом не владеет.
- Персонаж принадлежит миру, а не клиенту. Вход — занять свободный слот персонажа; при первом входе персонаж создаётся по шаблону. Перенос персонажа из другого мира не поддерживается.
- Выход игрока превращает его персонажа в обычного follower-npc под управлением AI. При возвращении управление возвращается. Механика уже существует — `avatar::control_npc` (`src/avatar.cpp:154`).
- Автосохранение выполняется на сервере по существующей настройке `AUTOSAVE_TURNS`.

## 7. Детерминизм

### 7.1 Источники недетерминизма и их закрытие

1. **Порядок итерации.** Любой обход, влияющий на симуляцию, идёт по `monsters_list` (`creature_tracker.h:148`, это `std::vector`) либо по явно отсортированному ключу. Обходы `monsters_by_location` (`:150`) и вложенного `unordered_map` по фракциям (`:164`) в сим-путях запрещены. Требуется аудит всех итераций по неупорядоченным контейнерам.
2. **RNG.** Единый глобальный `std::minstd_rand0` (`src/rng.cpp:210`), сид задаёт сервер. Вызовы `rng()` выносятся из UI-путей: превью, анимации, звук, отрисовка. Любой лишний вызов у одного участника сдвигает поток. Диагностируется счётчиком вызовов RNG в хеше состояния.
3. **Сортировка.** `std::sort` нестабилен при равных ключах. В сим-путях — только `std::stable_sort`.
4. **Указатели.** Адреса не совпадают между процессами и не могут использоваться как ключи сортировки или множеств. Требуется аудит.
5. **Плавающая точка.** `rng_float`, погода, `units::quantity<double>`. Флаги компилятора влияют на результат. `-ffast-math` запрещён, флаги зафиксированы, значения с плавающей точкой квантуются при хешировании.
6. **Часы.** `std::chrono` в `do_turn.cpp:682` используется для ограничения частоты опроса ввода. Должно быть проверено, что на состояние мира это не влияет, и запрещено к использованию в сим-коде.

Многопоточность источником проблем не является: симуляция однопоточная.

### 7.2 Хеш состояния

**Лёгкий хеш, каждый ход:** номер хода, счётчик вызовов RNG, состояние RNG, затем по всем существам в стабильном порядке — позиция, здоровье, moves; по игрокам дополнительно выносливость и усталость. Стоимость пренебрежимо мала.

Счётчик вызовов RNG — самый ценный элемент диагностики: он показывает не только факт расхождения, но и ход, на котором один из участников совершил лишний или недостающий вызов.

**Глубокий хеш, раз в 32 хода:** сериализация бабла и всех игроков в JSON и хеш от результата. Ловит расхождения, невидимые лёгкому хешу.

### 7.3 Детект и лечение десинка

Клиент отправляет хеш серверу, сервер сравнивает со своим. При расхождении сервер отправляет полный сейв, клиент перезагружается, игроки видят индикатор синхронизации. Операция дорогая, но редкая и безусловно работающая.

Обе стороны пишут лог: поток намерений и хеши по ходам. Любой десинк даёт воспроизводимое повторение, а не неуловимый плавающий сбой.

## 8. Тестирование

Поскольку одиночная игра намеренно не прогоняет мультиплеерный конвейер, ему нужен собственный страж в CI.

**Харнесс детерминизма.** Один процесс поднимает сервер и два клиента на loopback-транспорте, проигрывает скриптованные потоки намерений на тысячи ходов и сверяет хеши каждый ход. Обязательные сценарии: бой, крафт, сон, батч-ускорение, голосование за скип, отключение и переподключение игрока, принудительно вызванный десинк и его лечение.

**Фаззер намерений.** Генерация случайных валидных намерений, прогон, сверка хешей. Дёшево и результативно.

**Регресс одиночной игры.** 266 существующих тестовых файлов должны оставаться зелёными на всём протяжении работ. Это основной критерий того, что рефактор `choose`/`apply_intent` не изменил поведение.

## 9. План по фазам

| Фаза | Содержание | Критерий готовности | Недель |
|---|---|---|---|
| Ф−1 | Разведка: режется ли `choose`/`execute` на десяти худших действиях — прицеливание, крафт, разделка, вождение, строительство, чтение, торговля, установка, взлом, погрузка | Письменное заключение по каждому из десяти: режется / не режется / режется с оговоркой. | Ф0 | Каркас `src/mp/` за флагом сборки, loopback-транспорт, `mp_intent`, хеш состояния, скелет CI-харнесса | Харнесс гоняет пустую сессию и сверяет хеши | 2–3 |
| Ф1 | Разделение `choose` и `apply_intent` во всём слое действий | 266 тестов зелёные, поведение одиночной игры не изменилось | 5–8 |
| Ф2 | Второй `avatar`: `players`, `get_players()`, `nearest_player()`, сериализация нескольких игроков | Одиночный сейв читается как `players[0]`, мир с двумя персонажами сохраняется и загружается | 3–4 |

**Границы плана реализации.** Этот спек описывает целевую архитектуру, но не является заданием на все десять фаз сразу. Каждая фаза планируется отдельно, и до фазы Ф0 работа идёт по лестнице проверок, описанной ниже.

### 9.1 Лестница MVP

Фазам Ф0 и далее предшествуют три ступени, каждая из которых бьёт в собственный риск и заканчивается воротами. Порядок выбран так, чтобы оба смертельных риска были измерены до первых вложений в рефактор.

**Ступень MVP-0 — проба детерминизма. 3–7 дней.**

Мультиплеера нет, рефактора нет, одиночный игровой путь не изменяется. Добавляются только счётчик вызовов RNG поверх `rng_get_engine()`, функция `mp_state_hash()` по §7.2 и тест, прогоняющий фиксированный сейв с фиксированным сидом на 500 ходов при бездействующем игроке, записывая хеш каждого хода в файл. Бинарь запускается дважды, логи сравниваются.

Проверяет: детерминирован ли мир сам по себе — то есть фундамент §7 целиком. Дополнительно, прогон того же теста на второй машине с другим процессором и компилятором измеряет риск §10.2 (плавающая точка) на двадцать недель раньше, чем он всплыл бы на Ф7.

Ожидаемый результат — расхождение из-за обхода `monsters_by_location` (`creature_tracker.h:150`). Ценность ступени не в ответе «да или нет», а в измерении стоимости починки тем же инструментом.

Ворота: если детерминизм недостижим за разумную цену, весь подход с реплеем намерений отменяется и §5.3, §6, §7 переписываются под стриминг состояния.

**Ступень MVP-1 — разведка разрезаемости. 1–2 недели.** Это Ф−1 из таблицы выше.

Ворота: если инвариант §5.3 недостижим, дизайн ниже уровня §5.3 теряет силу и переписывается.

**Ступень MVP-2 — hotseat на два аватара. 4–7 недель.**

Два `avatar` в одном бабле, переключение управления клавишей, тезер и барьер. Ни сети, ни намерений, ни требований к детерминизму: симуляция одна, синхронизировать нечего. Требует Ф2, Ф4 и Ф6, но **не требует Ф1** — в hotseat каждый игрок исполняет действие немедленно, разрезание `handle_action` не нужно.

Проверяет: не разваливается ли игра от второго аватара, играбельна ли модель хода из §5.5 и §5.6, и каков настоящий объём Ф6 на практике, а не по результатам grep.

Побочный выигрыш: hotseat-кооп — самостоятельная работающая фича. Она сохраняет ценность даже если сетевая часть не будет доведена.

Ворота: если модель хода неиграбельна, пересматриваются §5.5 и §5.6 до вложений в сеть.

Сетевой вертикальный срез на пяти простых действиях рассматривался и отвергнут как первая ступень: он самый дорогой из вариантов и доказывает наименее спорное, поскольку движение и ближняя атака отделяются от UI тривиально, тогда как весь риск §10.1 сосредоточен в крафте, прицеливании и разделке.

Оставшиеся вызовы `get_avatar()` и `get_player_character()` в симуляционном коде, не вошедшие в Ф6, помечаются как `get_avatar_legacy()` и закрываются лит-правилом, запрещающим новые вхождения. Чинятся по мере всплытия багов.

## 10. Риски

1. **Ф1 не разрежется чисто.** Часть действий может требовать диалога с игроком посреди исполнения — например, подтверждения при обнаружении чего-то в процессе. Это ломает центральный инвариант. Именно поэтому Ф−1 идёт первой, до всякого каркаса. Если хотя бы одно из десяти проверяемых действий не режется, план пересматривается, а не подпирается частным исключением.
2. **Расхождение плавающей точки между разными сборками.** Смягчается единым билдом для всех участников и зафиксированными флагами компиляции. Остаточный риск принимается явно.
3. **Вливания из апстрима ломают инвариант.** Апстрим о нём не знает и будет добавлять действия с UI внутри исполнения. Смягчается кастомным clang-tidy-чеком, запрещающим вызовы UI из путей `apply_intent`. Инфраструктура для таких чеков в проекте уже есть.
4. **Постоянные конфликты при вливании из апстрима.** Смягчается минимизацией диффов в существующих файлах: максимум кода живёт в `src/mp/`.
5. **Мультиплеерный путь гниёт, потому что одиночная игра его не прогоняет.** Это прямое следствие требования изоляции режимов. Смягчается харнессом и фаззером из §8, которые обязаны быть готовы в Ф0, а не в конце.

## 11. Известные ограничения и принятые компромиссы

- **Нет серверного тумана войны.** Клиент физически держит весь бабл в памяти, поэтому модифицированный клиент видит всё. Для кооперативной игры без PvP это не имеет значения.
- **Клиенты обязаны быть идентичны серверу** по версии билда и набору модов. Хендшейк отказывает при несовпадении.
- **Free-roam закрыт.** Если игроки когда-либо должны разойтись по разным баблам, реплей намерений перестаёт работать, потому что клиенты будут симулировать разное, и потребуется стриминг состояния мира — оценочно плюс 12–20 недель и постоянный налог на каждое вливание из апстрима. Чтобы эта дверь не захлопнулась совсем, соблюдаются два условия: транспорт с первого сообщения версионирует протокол и допускает добавление нового типа потока данных, а сервер с самого начала является отдельным headless-процессом, а не «одним из клиентов, который заодно хостит».
- **Безопасность вне скоупа.** Предполагается доверенный круг игроков в LAN или через ZeroTier/Tailscale.
