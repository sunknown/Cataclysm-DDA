# Фаза 3a: планировщик с эстафетой — дизайн

Дата: 2026-08-08
Статус: утверждён к планированию
Родительский спек: `2026-08-04-cdda-p2p-coop-design.md`, разделы 5.4, 7, 9, 10, 11 (Ф3).
Предшественник: `2026-08-06-mp-phase2-context-design.md` (контекст игрока, выполнена).
Правки родителя, следующие из этого спека: §11 (Ф3 делится надвое), §5.4 (отдельный
поток ввода-вывода не заводится) — см. §11 ниже.

## 1. Контекст

Ф0–Ф2 сделаны. Сервер стримит экран, тонкий клиент играет по сети (ворота Ф1 пройдены
вечером одиночной партии через Tailscale), контекст игрока построен и доказан
самосравнением в обычной сборке. Остался механизм, ради которого всё это делалось:
**два игрока одновременно, каждый в своём меню, в одном мире.**

Родитель отводил Ф3 три-четыре недели на «планировщик с эстафетой, фаза мира как
участник» с воротами «два игрока на loopback, TSAN молчит». В ходе брейншторма фаза
выросла и была разделена:

- **Ф3a (этот спек)** — планировщик, разрез хода, барьер, мультиклиентский сервер.
  Ворота — живая партия вдвоём по TCP.
- **Ф3b (отдельный спек)** — вход в сессию: мир грузит сервер, меню входа на каждом
  клиенте, создание персонажа в своём контексте, один сейв на персонажа вместо
  вложенного массива `extra_players`.

Деление по живому шву: Ф3a доказывает спорную и новую механику, Ф3b делает её
пригодной для человека без дебаг-меню. Порядок выбран по правилу проекта — самое
рискованное измеряется первым и дёшево.

## 2. Скоуп

### В скоупе

- Снос цикла hotseat; сохранение всего многоаватарного фундамента под ним.
- Разрез `game::do_turn()` на четыре функции; одиночная игра ходит по тому же разрезу.
- Планировщик с эстафетой: поток на игрока, главный поток — мир и оркестратор.
- Барьер с правилом «активность или назначенный маршрут = отходил».
- «Тороплю» с видимым отсчётом; автоматический отсчёт при видимом враге.
- Белый список свободных действий в простое.
- `mp_session` — объект на сессию вместо процессных модулей экрана и ввода.
- Мультиклиентский сервер с фиксированным составом; слоты по `mp_hello.name`.
- Немодальный `debugmsg` в серверной сборке.
- Сессионный харнесс на N клиентов; прогон под ThreadSanitizer.

### Вне скоупа

| Что | Куда |
|---|---|
| Меню входа, создание персонажа, мир из меню, сейв на персонажа | Ф3b |
| Залипающее «ходите без меня», разгон долгих активностей, настройка длительностей | Ф4 |
| Вход и выход посреди партии, возврат после обрыва, наблюдатель после смерти, конфиг сервера | Ф5 |
| Тезер и якорь под N > 2 | Ф6; здесь переиспользуются как есть |
| Фаза планирования ходов (см. §10) | Кандидат, решается по итогам ворот |
| Клиентский сайдбар, тайлы, звук, персональные раскладки | Tiles-фаза и далее |

## 3. Сводка принятых решений

| Вопрос | Решение |
|---|---|
| Ворота фазы | Живая партия вдвоём по TCP с двух машин; отдельно ворота CI |
| Состав сессии | Фиксирован на старте: сервер ждёт N, обрыв или смерть любого заканчивает сессию |
| Разрез `do_turn` | Четыре функции, порядок одиночной игры сохранён точно |
| Кто ходит по разрезу | Оба билда. Одиночная игра — N=1 без потоков |
| Механизм переключения | Потоки со строгой эстафетой (решение родителя §5.4, не пересматривается) |
| Поток ввода-вывода | Не заводится: поток игрока сам себе I/O, пока не держит эстафету |
| Правило барьера | Тик, когда каждый живой *отходил* либо *не ждём* |
| «Планирование ходов» | Дешёвая версия: активность или дальняя цель движения считаются ходом |
| Простой у барьера | Цикл ввода жив; белый список ~20 свободных команд, остальное отклоняется |
| Состояние сервера | `mp_session` на клиента; связь с контекстом по индексу, не по указателю |
| Мир и слоты | Существующий путь `--world` (автозагрузка мимо меню); слот по `mp_hello.name` |
| Второй аватар | Переименованный дебаг-тоггл, локально, до старта сервера |
| Hotseat | Цикл удаляется; фундамент под ним переименовывается и остаётся |

### Отвергнуто

- **Фаза планирования ходов с призрачным аватаром** — см. §10. Не отвергнута навсегда:
  поставлена в зависимость от измерения на воротах.
- **Два пути хода** (`do_turn()` для одиночной игры, разрез под `MULTIPLAYER`) — дешевле
  и безопаснее для одиночной игры, но ветка не прогоняется обычными тестами. Ровно риск
  «гниение мультиплеерного пути» (родитель §12.5), против которого строилась Ф2.
- **Форма hotseat** (все действуют → `world_turn()` целиком → `avatar_turn`) — меньше точек
  разреза, но голова мира (календарь, погода, автосейв) сдвигается на после хода. Тогда
  одиночная игра по этому пути меняет поведение, и путей снова два.
- **Отдельный поток ввода-вывода** (родитель §5.4) — `mp_transport::recv( timeout_ms )`
  блокирующий и живёт на соединение, а поток игрока к моменту чтения уже отдал эстафету.
  Отдельный поток был бы механизмом без задачи.
- **Указатель на `mp_session` внутри `player_context`** — `player_context` живёт в обеих
  сборках и не должен знать сетевых типов.
- **Классификация всех 153 `action_id`** на дорогие и бесплатные — промах в сторону
  «бесплатно» даёт действие вне хода. Инвертировано в белый список (§7.3).
- **Парковка контекста *отходившего* на барьере** — дёшево, но «тороплю» негде нажать,
  и партнёр смотрит в мёртвый экран всё время чужого раздумья.

## 4. Снос hotseat

Идёт первым, до разреза `do_turn`: иначе разрез пришлось бы делать совместимым
с умирающим циклом.

Граница проходит не по имени. Собственно hotseat — это 94 строки цикла хода
(`src/mp/mp_hotseat_loop.cpp`). Всё остальное, что называется этим словом, — многоаватарный
фундамент, который родитель §4 явно перечисляет как переиспользуемый целиком.

### 4.1 Удаляется

- `src/mp/mp_hotseat_loop.cpp` и `.h`;
- развилка `mp_mode_active() ? mp_hotseat_do_turn() : g->do_turn()` (`src/main.cpp:714`)
  и включение заголовка (`src/main.cpp:50`);
- `friend bool mp_hotseat_do_turn();` (`src/game.h:201`);
- два теста, гоняющие сам цикл: `hotseat_turn_advances_calendar_once` и
  `hotseat_turn_drains_moves_from_every_slot` (`tests/hotseat_sim_test.cpp:124,162`).
  Перенацеливаются на новую функцию тика.

### 4.2 Переименовывается

## 5. Разрез хода

Ф2 §6.4 наметила `world_turn()` и `avatar_turn( avatar & )`. Уточняется до четырёх
функций: половинки нужны, чтобы порядок одиночной игры сохранился точно, а не примерно.
Источник — `game::do_turn()` (`src/do_turn.cpp:523-807`, 284 строки, ~42 обращения к `u`).

| Функция | Содержимое | Исполняется |
|---|---|---|
| `world_turn_pre()` | Календарь, `gamemode->per_turn`, музыка, кэш температур, `load_npcs`, `timed_events`, `item_wakeups`, `mission::process_all`, орды, немезида, автосейв, погода, сброс освещения, `perhaps_add_random_npc` | Главный поток, активного игрока нет |
| `avatar_turn_pre( ava )` | Угон транспорта, `stagger` из стены, испуг маунта, `update_body`, дожатие активности (`:611-613`), звуки NPC вокруг него, `process_sound_markers`, `sfx::do_hearing_loss` | Поток игрока, под его контекстом |
| *цикл действий* (`mp_player_act`) | `while( moves > 0 )`: `process_falling`, `cleanup_dead`, `mon_info_update`, звуки, взрывы, `ui_manager::redraw`, `handle_action`, `action_taken`, дожатие активности (`:632-700`) | Поток игрока |
| `world_turn_post()` | `build_floor_caches`, `process_falling`, `vehmove`, `process_fields`, `process_items`, `process_explosions`, `process_sounds`, `build_map_cache`, `monmove`, `overmap_npc_move`, `furniture_terrain_emit_fields`, `invalidate_visibility_cache` | Главный поток |
| `avatar_turn_post( ava )` | `process_turn` (восстановление moves), `handle_weather_effects`, `handle_progress_ui`, `update_bodytemp`, `update_body_wetness`, `apply_wetness_morale`, `update_morale`, `check_and_recover_morale`, `sfx`, `volume = 0`, баланс биоэнергии | Поток игрока |

Три места внутри `world_turn_post` требуют прохода по всем игрокам, а не по одному:
установка запаха (обязательно до `scent.update()`), `creature_in_field`, финальный
`mon_info_update`.

`is_game_over()` в голове `do_turn` читает `u`. В Ф3a смерть любого игрока заканчивает
сессию (§8.4), поэтому проверка становится проходом по слотам с той же семантикой.

### 5.1 Порядок тика

```
world_turn_pre()                        // мир, активного игрока нет
барьер открыт → N потоков, исполняется по одному за раз:
    avatar_turn_pre( ava )              // свой контекст, свой поток
    mp_player_act( ctx )                // эстафета уходит на get_input_event()
    паркуется у барьера
барьер выполнен (§7.2)
world_turn_post()                       // мир
для каждого игрока: эстафета → avatar_turn_post( ava ) → назад
якорь бабла на середину группы (mp_bubble_anchor)
```

Два места здесь неочевидны и оба вынужденные.

**`avatar_turn_post` не едет в поток игрока до барьера,** хотя это выглядело бы
симметрично: он восстанавливает moves, а в одиночной игре это происходит **после**
`monmove`. Отдать moves раньше — изменить правила. Поэтому после барьера главный поток
коротко передаёт эстафету каждому игроку второй раз за тик.

**`avatar_turn_pre` наоборот не может ехать на главном потоке:** дожатие активности
открывает окна (крафт спрашивает подтверждения), а окна существуют только в контексте
своего игрока. Отсюда общее правило фазы:

> Всё, что может открыть UI, исполняется в потоке своего игрока под его контекстом.

Правило проверяемо: нарушение ловится ассертом владения стеком из Ф2 §5.2
(`ui_adaptor` рождается и умирает под одним активным стеком).

## 6. Планировщик

`src/mp/mp_sched.{h,cpp}`.

Участников N+1. Главный поток — мир и оркестратор; по потоку на игрока, создаются при
старте сессии и живут до её конца. В каждый момент исполняется ровно один: право
исполняться — эстафета, передаваемая явно.

Реализация — мьютекс, `condition_variable` и `current_holder`. `yield_to( id )` отдаёт
эстафету и немедленно блокируется; `wait_for_turn( id )` просыпается, став держателем.
Настоящей параллельности нет по построению, поэтому мутация мира остаётся строго
последовательной, как в одиночной игре.

### 6.1 Единственная точка передачи

Серверный бэкенд `input_manager::get_input_event()` (`src/mp/mp_curses_server.cpp`):

```
сбросить композитный экран сессии в сокет   // игрок видит, что игра нарисовала
отдать эстафету
transport.recv( timeout_ms )                // блокируемся, ничего не держа
забрать эстафету
вернуть событие
```

Отсюда следует отказ от отдельного потока ввода-вывода (родитель §5.4):
`mp_transport::recv( timeout_ms )` блокирующий и живёт на соединение
(`src/mp/mp_transport.h:26`), а поток игрока к моменту чтения эстафету уже отдал. Он сам
себе поток ввода-вывода, пока не исполняется. Медленный сокет по-прежнему не тормозит
симуляцию: держатель эстафеты в это время — кто-то другой.

Сброс экрана ровно в этой точке даёт бесплатную дедупликацию, как и в Ф0: десяток
перерисовок внутри одного действия схлопывается в одну посылку.

### 6.2 Одиночная игра

При N=1 потоков не создаётся вовсе: оркестратор зовёт `mp_player_act()` инлайном.
Один и тот же код, два способа запуска. Это то же решение, что и в Ф2 с контекстом,
и по той же причине: разрез и порядок тика прогоняются всеми 266 тестовыми файлами
каждый прогон, а не только серверной сборкой.

### 6.3 Диагностика

- `cata_assert( sched.holder() == std::this_thread::get_id() )` в `mp_activate_player`
  и на входе `get_input_event` — ловит «исполняется, не держа»;
- сторожевой таймер отдельным потоком: если эстафета не двигалась дольше порога, в лог
  пишется её держатель — ловит «держит и не отдаёт».

Два режима отказа, оба громкие и диагностируемые. Молчаливой порчи состояния
планировщик не допускает по построению.

### 6.4 Замер стоимости свопа

Ф2 риск 5 закрывается здесь. Своп аватара — три move целого `avatar`
(`game::swap_slot_into_u()`, `src/game.cpp:4634-4649`), и теперь он на горячем пути:
минимум 2N свопов на тик. Замер входит в фазу; при плохом результате пересматриваем
в пользу аксессора вместо контент-свопа (Ф2 §2, «Отвергнуто»).

**Замерено (2026-10-27).** `swap_cost_is_measured` (`tests/mp_swap_benchmark_test.cpp`,
скрытый тег `[.][mp][benchmark]`): пара `mp_activate_player( 1 )` / `mp_activate_player( 0 )`
стоит **12,2 мкс** в среднем (100 сэмплов, σ 3,0 мкс) в отладочной сборке `-Og`, то есть
около 6 мкс на своп. Порог плана — 50 мкс на пару; при двух игроках это ~25 мкс на тик.
Аксессор не нужен, риск 5 Ф2 закрыт.

## 7. Модель хода

### 7.1 Состояния игрока

Выводятся из состояния, а не хранятся отдельно:

- *действует* — есть moves, контекст исполняется;
- *отходил* — moves ≤ 0, **либо** есть активность, **либо** назначена дальняя цель
  движения (`has_distant_destination()`, `src/do_turn.cpp:649`);
- *держит* — есть moves, контекст стоит на ожидании ввода;
- *не ждём* — снят с барьера по «тороплю».

### 7.2 Барьер

**Мир тикает, когда каждый живой игрок либо *отходил*, либо *не ждём*.**

Второе и третье условия *отходил* — принципиальные, а не оптимизация. Ход в CDDA — это
типично одно действие (аватар получает ~100 moves за тик, шаг стоит ~100), а листание
меню времени не тратит. Без них игрок, открывший инвентарь, остаётся *держит*
и морозит партнёра на всё время чтения. С ними игрок назначает маршрут или начинает
долгое дело, уходит в меню, персонаж продолжает действовать — партнёр не заморожен.

Это дешёвая версия «фазы планирования ходов» (§10), собранная из механик, которые
в игре уже есть и уже отлажены.

### 7.3 «Тороплю» и простой

Любой *отходивший* может нажать «тороплю». Это запускает видимый обратный отсчёт
у всех, кто *держит*. По истечении сервер **не лезет в чужой UI и ничего не закрывает** —
он снимает этих игроков с обязанности держать барьер на этот тик. Персонаж стоит
и пропускает ход, меню остаётся открытым, игрок дочитывает список и подтверждает выбор,
когда ему удобно. Цена — выбранное может протухнуть; игра ответит обычным сообщением
об отказе, как и в одиночной игре.

Пока в бабле есть враждебное существо, которое кого-то из игроков видит, отсчёт
запускается автоматически и он короче. Никто не тратит нажатие, когда на него бегут.

**Цикл ввода *отходившего* не останавливается.** Работает белый список свободных команд:
инвентарь, лист персонажа, карта, осмотреться, сообщения, настройки, помощь, зум,
«тороплю». Всё прочее отклоняется сообщением «вы уже ходили в этом ходу».

Список строится инверсией: умолчание — «стоит времени», перечисляются только свободные.
Классифицировать все 153 значения `action_id` (`src/action.h:22`) и дорого, и опасно —
промах в сторону «бесплатно» даёт действие вне хода. При инверсии промах даёт отказ:
неудобно, но не эксплойт, и чинится одной строкой.


**Что сделано в Ф3a, а что нет (2026-10-27).** Клавиша «тороплю» — `` ` `` (действие
`coop_hurry`): `'` занята `ignore_enemy` в том же режиме ввода. Абзац выше Ф3a не выполнила:
*отходивший* отдаёт эстафету и паркуется до следующего хода, клавиш он не читает, поэтому
нажать «тороплю» может только тот, кто ещё *держит*. Это переносится в Ф4 вместе с «ходите
без меня» — новый путь ввода для припаркованного игрока, а не правка.

Снятие с барьера, в отличие от «на этот тик» выше, живёт, пока игрок сидит в том же
ожидании ввода: одно нажатие не должно покупать ровно один тик. Его клавиши при этом
читаются — мир отдаёт ему эстафету, когда он вернулся с нажатием, не делая его условием
барьера. Если играть некому — все живые сняты или заняты активностью, — ход длится не меньше
длины отсчёта (4 с в бою, 15 с иначе): иначе мир крутил бы ходы со скоростью CPU вокруг
думающего игрока (ревью 2026-10-27, решение пользователя: залипание плюс темп).

### 7.4 Видимость состояний

Все состояния видны всем. Виджет `coop_player_desc` (§4.2) расширяется до строки
«ждём: игрок X» с отсчётом, когда он идёт.

## 8. Сессия и сеть

### 8.1 `mp_session`

`mp_server_screen` и `mp_server_input` перестают быть процессными модулями
(`src/mp/mp_server_screen.h:50-52` признаёт это состояние явно) и становятся объектом
на клиента: транспорт, сетка ячеек с построчным отслеживанием изменений, курсор,
схлопывание бэклога (`MP_SCREEN_BACKLOG_BYTES`), буфер ввода, запрос резайза, имя из
`hello`, индекс своего контекста.

**Связь контекста с сессией — по индексу, не по указателю.** `player_context` живёт
в обеих сборках (Ф2 §6.7) и не должен знать сетевых типов. Серверный бэкенд держит
массив сессий, параллельный `game::contexts` (deque, адреса стабильны — Ф2, нота 4);
`mp_active_session()` — сессия по индексу активного контекста.

Три шва бэкенда переходят с глобального состояния на активную сессию:
`curses_drawwindow()` пишет в её сетку, `get_input_event()` читает её сокет, сброс
экрана уходит в её транспорт.

### 8.2 Старт сессии

`--server <port> --world <name> --players N`.

Сервер слушает, принимает до N соединений, каждому делает существующий handshake
(`mp_server_handshake`), создаёт контекст и сессию. Собрав всех — грузит мир существующим
путём: `main_menu::queued_world_to_load` (`src/main.cpp:692`) уже автозагружает мир мимо
главного меню (`src/main_menu.cpp:646-661`). Затем раздаёт слоты по `mp_hello.name`
(`src/mp/mp_protocol.h:37-43`) среди аватаров в сейве, поднимает потоки, входит в цикл
тиков. Имя не совпало — отказ с внятным текстом. Пока собрались не все, сервер ждёт
неограниченно и пишет в консольный лог, кого не хватает: льготные интервалы и таймауты
подключения — работа Ф5 вместе с остальным жизненным циклом.

Работы по меню в Ф3a нет: существующий путь годится как есть. Ф3b заменяет и его,
и раздачу слотов на меню входа с созданием персонажа.

Второй аватар кладётся в сейв заранее, локально, переименованным дебаг-тогглом (§4.2).

### 8.3 Резайз

Каждый игрок получает экран своего размера — механизм из Ф1 и Ф2 без изменений,
теперь применяемый к сетке своей сессии и окнам своего контекста
(`mp_resize_active_context()`).

### 8.4 Обрыв и смерть

Состав фиксирован. Обрыв любого клиента или смерть любого игрока заканчивают сессию:
остальные получают `bye` с причиной, сервер корректно сохраняется и выходит.

**Как сделано (2026-10-27).** Сервер не выходит, а возвращается в меню, как после конца
одиночной игры. Смерть в сессии не идёт одиночным путём: экраны смерти, deathcam и меню
WORLD_END спрашивают одного игрока, а перенос сейва на кладбище унёс бы вместе со слотом 0
всех напарников. Мир сохраняется как есть, вместе с мёртвым персонажем, а его смерть
обрабатывается при следующей одиночной загрузке. Вопросы, которые задаёт сам мир (NPC
заводит разговор, вопрос монстра, попап эффекта в `avatar_turn_post` на потоке мира),
получают ответ Escape и строку в консоли сервера: отвечать некому, а маршрутизация вопроса
к игроку, которого он касается, — работа следующих фаз.

Ни парковки контекста, ни раскрутки чужого стека через `ESC`, ни перевода в follower-npc,
ни наблюдателя после смерти — это §8.3, §8.4 и §9 родителя, они целиком Ф5. Фиксированный
состав выбран именно затем, чтобы Ф3a не начала их реализовывать по частям.

### 8.5 `debugmsg`

В серверной сборке `debugmsg` перестаёт быть модальным: пишет в лог и рассылает строку
в сообщения всем игрокам, но никогда не блокирует. Сейчас `src/debug.cpp` не знает
о `MP_SERVER` вовсе.

Это не полировка. Ошибка в фазе мира срабатывает, когда ни один контекст игрока
не активен и показывать окно физически некуда, — мгновенный тупик сессии (родитель §9).

## 9. Тестирование

Ворота фазы двойные.

**Ворота человека:** вечер игры вдвоём по TCP с двух машин. Спорное место Ф3a — не
механика эстафеты (её доказывают TSAN и ассерты), а ощущение одновременности: играбельно
ли, когда один сидит в крафте, а второй ходит по улице. Это видно только человеку. Тот же
приём, которым проект выиграл на воротах Ф1.

**Ворота CI:** loopback-харнесс, TSAN молчит, 266 тестовых файлов зелёные.

### 9.1 Сессионный харнесс

Рабочая лошадка: сервер и N клиентов в одном процессе на loopback-транспорте,
скриптованные потоки нажатий, проверки и по состоянию мира, и по экранам.
**В транспорт закладывается искусственная задержка** — иначе неизбежно напишется код,
работающий только при нулевом RTT.

### 9.2 Полнота контекста на двух игроках

Расширение ворот Ф2 с одного контекста на два: сценарий открывает разные меню у двух
игроков, чередует их нажатия и сверяет буфер экрана каждого с эталоном того же меню,
снятым в одиночной сессии. Протёкший глобал меняет картинку и виден сразу. Список тяжёлых
меню: инвентарь, крафт, карта, лист персонажа, транспорт, строительство.

### 9.3 Строгость эстафеты

Прогон харнесса под ThreadSanitizer. Поскольку в каждый момент исполняется ровно один
контекст, TSAN обязан молчать; любое срабатывание — настоящая пропущенная передача
управления. Дешёвые и решающие ворота в CI.

### 9.4 Барьер

Правило «активность или маршрут = отходил», «тороплю» и снятие с барьера,
автоторопление при видимом враге, белый список простоя.

### 9.5 Регресс одиночной игры

266 тестовых файлов зелёные. Это и есть доказательство, что порядок хода сохранён:
одиночная игра ходит по новому разрезу (§6.2), поэтому проверяет его каждый прогон.

### 9.6 Замер свопа

Микробенчмарк `mp_activate_player` на реальном `avatar`; закрывает Ф2 риск 5 (§6.4).

## 10. Фаза планирования ходов

Рассмотрена и отложена с явным условием пересмотра — записано, чтобы не обсуждать заново.

**Предложение.** Шаг не выполняется мгновенно: игрок сначала планирует, куда пойдёт
(по образцу «осмотреться» — двигается камера, целевая клетка подсвечивается приглушённым
аватаром), затем явно подтверждает ход. Все подтвердили — все походили. Игрок в меню
с уже запланированным маршрутом не задерживает остальных.

**Что в ней верно.** «Я принял решение» и «я сижу за клавиатурой» — разные вещи, и барьер
их путает. Это лучше поставленный вопрос, чем ленивый таймаут родителя §7.3, который
наказывает думающего потерей хода.

**Почему не сейчас.**

1. Планируется только движение, а блокирует не только оно. Удар, дверь, подбор, выстрел,
   бросок, перезарядка, еда, бионика, осмотр — при луте дома движение хорошо если половина
   ходов. Чтобы закрыть остальное, планировать надо любое действие, а это разрез
   choose/execute, забракованный MVP-1 (крафт 1 M-обращение и 22 A, транспорт 5 M,
   строительство 2 M и 5 A).
2. Одновременное разрешение — правила, которых в движке нет. Двое в одну клетку; A шагает
   туда, откуда уходит B. Лечится разрешением в порядке слотов, но тогда одновременность —
   иллюзия интерфейса.
3. Планирование по устаревшей доске. Либо B не видит хода A и планирует по неправде, либо
   видит — и «фаза планирования» это отложенное действие, а порядок снова значим.
4. Трогает `avatar_action::move` и путь ввода движения — самый исхоженный код в CDDA
   и самый конфликтный при вливании апстрима (родитель §12.6). Режим только под
   мультиплеером дал бы второй UI-путь движения, то есть риск §12.5 в главной механике.
5. Цена сопоставима со всей Ф3a.

**Условие пересмотра.** После ворот Ф3a будет известно то, чего сейчас никто не знает:
какая доля ходов в реальной кооп-партии — движение, и сколько времени партнёр реально
проводит в ожидании. Если правила §7.2 не хватает — фаза планирования становится
обоснованной отдельной фазой с измеренной пользой. Если хватает — сэкономлены недели
на самом опасном участке кода.

## 11. Требуемые правки родительского спека

- **§11 (план по фазам).** Ф3 делится на Ф3a (этот спек, 4–5 недель) и Ф3b (вход
  в сессию, 2–3 недели). Ворота Ф3a — живая партия вдвоём по TCP, а не только loopback:
  спорное здесь — ощущение одновременности, и оно измеряется человеком.
- **§5.4.** «Сеть работает отдельным потоком ввода-вывода» отменяется: при потоке
  на игрока этот поток — механизм без задачи (§6.1).
- **§7.3.** Ленивый таймаут переезжает из Ф4 в Ф3a вместе с барьером. Голый барьер
  без механизма снятия делает вечер вдвоём непроходимым (§7.2), а ворота Ф3a — это
  как раз вечер вдвоём.
- **§8.1.** Модель хранения (`extra_players` внутри сейва слота 0 против одного сейва
  на персонажа) пересматривается в Ф3b. Обещание «одиночный сейв можно отдать серверу
  и наоборот» сегодня половинчатое: напарник заперт в чужом файле и в соло не играется.

## 12. Риски

1. **Пропущенная точка передачи эстафеты.** Режим отказа — зависание, то есть громкая
   и диагностируемая ошибка, а не молчаливая порча состояния. Ловится сторожевым
   таймером и ассертом «исполняется, не держа» (§6.3).
2. **UI, открытый не в своём потоке.** Правило §5.1 («всё, что открывает UI, — в потоке
   своего игрока»); нарушение ловит ассерт владения стеком из Ф2 §5.2.
3. **Разрез меняет поведение одиночной игры.** Главный риск фазы: `do_turn` — центральная
   функция игры. Митигируется тем, что порядок сохранён точно (§5.1), и тем, что одиночная
   игра ходит по новому пути, а значит 266 тестов проверяют его каждый прогон.
4. **Стоимость свопа на горячем пути.** Замеряется в этой фазе (§6.4); при плохом
   результате — аксессор вместо контент-свопа.
5. **Неполный белый список простоя.** Безопасен по построению (§7.3), чинится строкой.
6. **Конфликты при вливании апстрима.** `src/do_turn.cpp` становится вторым содержательным
   диффом после `src/cata_imgui.cpp`. Осознанная цена решения «один путь для всех»;
   альтернатива — гниющая мультиплеерная ветка.

## 13. Границы

- Меню входа, создание персонажа в контексте, загрузка мира сервером, один сейв
  на персонажа — Ф3b, отдельный спек.
- Залипающее «ходите без меня», разгон долгих активностей, настройка длительностей
  отсчётов — Ф4.
- Вход и выход посреди партии, возврат после обрыва с раскруткой стека через `ESC`,
  перевод в follower-npc, наблюдатель после смерти, конфигурационный файл сервера — Ф5.
- Тезер и якорь под N > 2 — Ф6; в Ф3a переиспользуются как есть.
- Клиентский сайдбар, разрез `widget::sample`/`layout`, тайлы — tiles-фаза.
- Персональные раскладки, звук у клиентов, шифрование и аутентификация — как в родителе,
  вне скоупа.
