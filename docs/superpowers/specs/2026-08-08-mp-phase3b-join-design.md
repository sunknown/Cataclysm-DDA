## 1. Контекст

Ф3a даёт партию вдвоём по TCP, но добраться до неё можно только вручную: мир и второй
аватар готовятся заранее в обычной сборке дебаг-тогглом, сервер поднимается с `--world`,
слоты раздаются по имени персонажа из `hello`. Играбельно для разработчика, непригодно
для человека.

Ф3b закрывает это: мир грузит сервер, а каждый клиент получает **своё** меню входа,
в котором создаёт персонажа или продолжает за своего. Это §8.2 родителя («Вход»),
переехавшая из Ф5, плюс смена модели хранения персонажей, без которой она не собирается.

Фаза выделена из Ф3 при брейншторме 2026-08-08 вместе с Ф3a: Ф3a доказывает спорную
и новую механику, Ф3b делает её пригодной для человека. Порядок — по правилу проекта:
самое рискованное измеряется первым и дёшево.

## 2. Скоуп

### В скоупе

- Разрез `game::load( save_t )` на мировую и персональную части.
- Один сейв на персонажа; массив `extra_players` перестаёт читаться и писаться.
- Меню входа `mp_join_menu` на каждом клиенте, в его контексте.
- Создание персонажа: custom, preset (шаблон), random.
- Продолжение за своего персонажа по карточке, которую клиент держит у себя.
- Кооперативный сценарий отдельным JSON-файлом; список сценариев в меню фильтруется.
- Размещение новых персонажей вплотную к группе, с фолбэком по спирали.
- Сведение продолжающих персонажей в один бабл.
- Сохранение всех N персонажей: автосейв и выход.

### Вне скоупа

| Что | Куда |
|---|---|
| Вход и выход посреди партии, возврат после обрыва, наблюдатель после смерти | Ф5 |
| Создание и выбор мира, моды, спец-режимы, кредиты | Не вводится: мир задаётся `--world` |
| Персональные раскладки, звук у клиентов, клиентский сайдбар, тайлы | Как в родителе |
| Более одного кооп-сценария | Первый этап — один |

## 3. Сводка принятых решений

| Вопрос | Решение |
|---|---|
| Когда начинается партия | Когда все N выбрали персонажа. Готовые видят экран ожидания |
| Модель хранения | Один файл сейва на персонажа, как в ванильном мире |
| Старые хотсит-сейвы | `extra_players` игнорируется, строка в лог; второй персонаж теряется |
| Меню входа | Новый `mp_join_menu`, а не режим `main_menu` |
| `Load character` | Продолжение за своего по карточке, а не выбор из списка чужих |
| Что клиент хранит | Карточку: адрес сервера, имя мира, `save_id`, имя персонажа |
| Кто авторитетен | Сервер, всегда. Карточка — опознавательный жетон, не источник правды |
| Settings в меню | Серверные опции, любой участник может менять |
| Сценарий | Один кооп-сценарий, новым файлом; список в меню фильтруется |
| Размещение | Два прохода после того как все выбрали: продолжающие по своим сейвам, новые — вплотную к опорному |
| Полный `start_game()` | Только когда мир пуст, и только для первого нового персонажа |
| Разошедшиеся продолжения | Сводятся к опорному, с явным сообщением всем до старта |
| `Quit` в меню входа | Сессия снимается, место освобождается, сервер ждёт снова |

### Отвергнуто

- **Режим `main_menu` вместо нового меню.** `main_menu` сцеплен с выбором мира, созданием
  мира, модами и спец-режимами; переиспользовать его пришлось бы вместе со всем этим.
  Из существующего берётся то, что действительно нужно: `avatar::create()` и список
  шаблонов.
- **`Load character` как список `world_saves`.** Первая формулировка при брейншторме.
  Отвергнута в пользу продолжения по карточке: чужого персонажа выбрать нельзя
  в принципе, и вопрос «занят другим клиентом» не возникает.
- **Полный сейв персонажа на клиенте.** Персонаж без мира неиграбелен — позиция, миссии,
  фракции и память карты ссылаются на тот мир, — поэтому как путь восстановления это
  не работает. Плюс появился бы вопрос «чья копия главнее» при расхождении. Карточка
  даёт всю нужную механику и не может устареть.
- **Миграция старых хотсит-сейвов.** Формат создаёт только дебаг-тоггл, релизных сейвов
  нет, второй аватар пересоздаётся за минуту. Решено 2026-08-08.
- **Ограничение сценария через `scen_blacklist`.** Механизм существует
  (`src/scenario.h:181-190`), но это мод-хук, и в `data/` его не использует никто.
  Фильтрация списка на стороне сервера дешевле и не трогает загрузку контента.
- **Готовые игроки входят в мир, не дожидаясь остальных.** Это вход посреди партии
  целиком: слот добавляется к живой симуляции, тезер надо где-то проявить, барьер меняет
  размерность посреди тика. Ф5.

## 4. Разрез загрузки и сохранения

`game::load( save_t )` (`src/game_io.cpp:325-420`) смешивает три уровня: мировое
(`load_master()` — фракции, `load_dimension_data()` — погода и состояние овермапа,
`init_autosave()`, `gamemode`), персональное (`u = avatar()`, `set_save_id`,
`unserialize()`, память карты, дневник, мемориал, `recalc_sight_limits()`) и финализацию.

Режется на два:

```cpp
// Once per world, before any character exists: factions, dimension data,
// weather, overmap state, autosave, gamemode.
bool load_world_state();

// Once per player, under that player's context. Replaces the slot's avatar with
// the one in the save, then loads their map memory, diary and memorial.
//
// Must run with slot `slot` active: unserialize() reads `u`, and `u` is whichever
// slot the context swap put there. This is the Phase 2 mechanism used for its
// purpose.
bool load_character( const save_t &name, size_t slot );
```

Порядок на сервере: `set_active_world` → `g->setup()` → `load_world_state()` → по игроку
`mp_activate_player( i )` и `load_character( save, i )`.

Сохранение симметрично: `game::save()` пишет `u`, поэтому сохранение N персонажей — цикл
«активировать контекст `i` → сохранить». Один и тот же цикл обслуживает автосейв в фазе
мира и сохранение при выходе.

### 4.1 Массив `extra_players` умирает

`savegame.cpp:151-154` (запись) и `:326-329` (чтение) удаляются. `unserialize` становится
чисто персональным — и **без этого разрез не сходится**: пока чтение персонажа тянет
за собой чужих аватаров, «персональная часть» не персональна.

Встретив сейв с `extra_players`, сервер пишет в лог, что мир создан прежним форматом
и дополнительные персонажи в нём проигнорированы, и грузится как одиночный. Отдельного
кода миграции нет (§3, «Отвергнуто»).

Следствие обоюдное и оно же — исполнение обещания родителя §8.1: кооп-мир становится
буквально обычным миром с несколькими персонажами. Любого можно взять и в соло, и в кооп;
напарник больше не заперт внутри чужого файла.

## 5. Слоты и контексты: порядок создания

Здесь ловушка, которую надо назвать: Ф2 держит `game::contexts` параллельно
`game::player_slots`, но меню входа рисуется **до** того, как персонажи существуют,
а слота без персонажа не бывает.

Решение: сервер создаёт **N пустых слотов** сразу после загрузки мира (`add_player_slot()`
возвращает свежий `avatar`, а пустой аватар — ровно то, что заполняет создание персонажа),
затем `mp_sync_context_count()`, затем поднимает потоки с меню входа. Меню слота `i` либо
заполняет его через `avatar::create()`, либо заменяет содержимое через
`load_character( save, i )`. Инвариант Ф2 не нарушается ни на одном шаге.

## 6. Меню входа

`src/mp/mp_join_menu.{h,cpp}`. Исполняется в контексте своего игрока, в его потоке,
и стримится ему как любой другой экран.

```
New character
    Custom character      -> character_type::CUSTOM
    Preset character      -> character_type::TEMPLATE (список шаблонов)
    Random character      -> character_type::RANDOM
Continue as <name>        -> продолжение по карточке; пункта нет, если карточки нет
                             или названного ею персонажа в мире нет
Settings                  -> серверные опции
Help
Quit
```

Создание персонажа своего кода не требует: `character_type::CUSTOM` / `RANDOM` /
`TEMPLATE` (`src/enums.h:481-487`) и `avatar::create( type, template_name )` — тот же UI,
что в одиночной игре, просто в контексте своего игрока. Это ровно то, что обещал
родитель §8.2.

Отсутствует по сравнению с ванильным меню: выбор и создание мира, моды, спец-режимы,
кредиты. Мир фиксирован `--world`.

**`Settings` открывает серверные опции, и любой участник может их менять.** Согласуется
с Ф2 §6.6 («опции общие, кроме перечисленных») и не требует нового кода. Клиентские
величины — шрифт, тайлсет, размер окна, DPI — сервер физически изменить не может, они
живут в клиентском процессе. Самое опасное из общего, ширина сайдбара, уже закрыто
в серверной сборке (Ф2 §6.5).

**`Quit`** отключает этого клиента. Партия ещё не идёт, симуляции нет, поэтому сервер
не заканчивает работу: он снимает сессию, освобождает место и снова слушает. Это не
противоречит фиксированному составу Ф3a — состав фиксируется в момент старта партии,
а не в момент первого подключения.

### 6.1 Экран ожидания

Игрок, закончивший выбор, видит экран со списком тех, кого ещё ждут. **Протокол для этого
не меняется**: это обычный нарисованный экран в его контексте, уезжающий обычным путём
дельт ячеек. `status`-сообщение остаётся долгом Ф4.

Барьера в фазе входа нет: планировщик Ф3a перебирает тех, кто ещё не закончил. Барьер
включается вместе с первым тиком мира.

## 7. Карточка персонажа

Клиент держит у себя не сейв, а опознавательный жетон.

```cpp
// What the client remembers about a character it plays on some server. Enough to
// say "I am this survivor" on the next connect, and nothing more: a character
// save without its world is unplayable, so keeping one would be a backup that
// cannot restore anything.
struct mp_character_card {
    std::string server;          // host:port, as typed into --connect
    std::string world_name;
    std::string save_id;         // matches save_t::decoded_name() on the server
    std::string character_name;  // for the menu line, and for the log
};
```

Живёт в клиентской userdir. Один файл на сервер-и-мир, поэтому «ваши персонажи на разных
серверах» получается списком файлов.

Протокол дополняется минимально:

- `mp_hello` получает поле `save_id` — сервер ищет по нему персонажа в мире;
- новое сообщение сервер→клиент `character_card`, несущее поля выше. Посылается **в момент,
  когда персонаж установлен**, а не при выходе: за партию карточка не меняется, а ранняя
  отправка переживает падение сервера.

**Сервер авторитетен всегда.** Карточка, указывающая на персонажа, которого в мире нет,
вырождается в «создай нового» — не в ошибку и не в отказ подключения. Расхождения между
копиями не бывает, потому что второй копии нет.

## 8. Размещение персонажей

`game::start_game()` (`src/game.cpp:808-900`) **нельзя вызывать на загруженном мире**:
он делает `start_calendar()`, `seed = rng_bits()`, `overmap_buffer.init_region_layout()`,
сбрасывает `dimension_prefix`, а в ветке неудачного поиска старта — `MAPBUFFER.clear()`
и `overmap_buffer.clear()`. На существующем мире это сброс календаря и стирание карты.

Персональное в нём есть и нужно: `u.setID( assign_npc_id() )`, `add_profession_items()`,
`migrate_items_to_storage()`, поиск стартовой локации, `place_player`.

Персональная часть выносится:

```cpp
// Establishes a freshly created character in a world that already exists.
//
// With `near` unset this is the scenario's own start location and the full
// world-building path (only ever the first character in an empty world).
// With `near` set it skips every world-scoped step -- no start_calendar, no
// init_region_layout, no load_map, no MAPBUFFER.clear -- and puts the character
// next to that point.
//
// Also what Phase 5 needs for a replacement character after a death (parent §8.4).
bool place_new_character( avatar &ava, std::optional<tripoint_abs_ms> near );
```

Размещение идёт **в два прохода, и только после того как все выбрали** (§9). Один проход
не годится: слоты раздаются по порядку подключения, а не по тому, кто продолжает,
поэтому «позиция слота 0» ничего не значит — слот 0 может оказаться новым персонажем,
у которого позиции ещё нет.

**Проход 1 — продолжающие.** Каждый получает позицию из своего сейва. Первый из них
становится **опорным**: точкой, к которой привязываются все остальные.

**Проход 2 — новые.** Если опорный есть, каждый новый ставится вплотную к нему:
`place_new_character( ava, позиция опорного )`. Если опорного нет (мир пуст, все
персонажи новые), первый новый идёт полным путём `start_game()` — календарь, стартовая
локация сценария, постройка мира — и сам становится опорным; остальные привязываются
к нему.

Итого четыре случая, и мировые шаги исполняются ровно один раз и только когда мир пуст:

| Случай | Что исполняется |
|---|---|
| Продолжение за своего | Позиция из сейва; первый такой становится опорным |
| Новый персонаж, опорный есть | `place_new_character( ava, позиция опорного )` — без единого мирового шага |
| Новый персонаж, опорного нет | Полный `start_game()`; становится опорным |
| Продолжения, разошедшиеся по миру | Все, кроме опорного, сводятся к нему (§8.3) |

### 8.1 Кооперативный сценарий

Отдельный сценарий заводится **новым файлом** `data/json/scenarios_coop.json`, а не правкой
`data/json/scenarios.json`: последний апстрим тоже правит, и новый файл конфликтов
не создаёт. Стартовая локация переиспользует существующий `om_terrain: "shelter"`
(как `sloc_shelter_safe`, `data/json/start_locations.json`) — место безопасное
и вместительное.

Список сценариев в меню входа фильтруется до кооперативных на стороне сервера.

**Сценарий не даёт соседних тайлов.** Любой сценарий выбирает **одну** стартовую локацию
на персонажа, `find_player_initial_location()` рандомизирует OMT, и даже при одном OMT
`place_player` сам ищет место внутри; понятия «группа» у сценариев нет. Пара работает
так: сценарий гарантирует, что точка безопасна и вместительна, а `place_new_character`
ставит остальных вплотную. Сценарий не заменяет код размещения, а делает его работу
тривиальной.

### 8.2 Фолбэк размещения

Пол шелтера конечен, и запрошенный соседний тайл может быть занят, непроходим или вне
карты. Размещение идёт поиском по расширяющейся спирали от целевой точки с проверкой
проходимости и отсутствия другого существа. Без этого двое встанут в одну клетку или
в стену.

Радиус поиска ограничен мягким пределом тезера (32 тайла, родитель §7.6): дальше него
размещать бессмысленно, потому что тезер тут же начнёт возражать. Не нашлось места —
отказ с внятным текстом в меню входа, а не молчаливое размещение неизвестно где.

Спираль обязана проверять и **занятость другим только что размещённым игроком**, а не
только проходимость: проход 2 ставит персонажей по очереди, и второй новый ищет место,
когда первый уже стоит, но ещё не участвует ни в одном кэше существ.

### 8.3 Разошедшиеся продолжения

Двое продолжают за персонажей, которых играли соло в разных концах карты. Бабл один
(132×132 тайла), тезер нарушен до первого хода.

Сервер оставляет на месте **опорного** (первого продолжающего, §8) и сводит к нему
остальных через тот же `place_new_character` — «выжившие нашли друг друга», штатный
для CDDA способ появления, на который опирается и родитель §8.4.

**Говорится об этом всем, до старта.** Молча телепортировать чужого персонажа нельзя:
это его сейв, и он должен узнать об этом в меню входа, а не обнаружить постфактум. Кого
именно сдвинули — видно в строке подтверждения; несогласный жмёт `Quit` и не играет,
а не узнаёт о переносе на пятой минуте.

## 9. Порядок старта сессии

```
bind → accept N → handshake каждому (mp_hello с save_id)
     → set_active_world( --world ) → g->setup() → load_world_state()
     → N пустых слотов + mp_sync_context_count()
     → потоки: mp_join_menu в своём контексте
     → все готовы
     → размещение (§8) → character_card каждому → цикл тиков Ф3a
```

## 10. Тестирование

**Ворота:** двое подключаются к серверу с голым миром, каждый у себя создаёт персонажа
с нуля, партия начинается и играется. Второй прогон на том же мире — оба продолжают
за своих.

Тесты:

1. **Разрез загрузки.** Мир с двумя сохранёнными персонажами грузится в два слота;
   у каждого слота свой аватар, позиции взяты из своих сейвов, состояние мира загружено
   один раз.
2. **Круговой рейс сохранения.** N персонажей сохраняются в N файлов и загружаются
   обратно с тем же содержимым.
3. **Старый формат.** Сейв с `extra_players` грузится как одиночный, пишет строку в лог
   и не падает.
4. **Размещение.** Новый персонаж в непустом мире оказывается в пределах мягкого предела
   тезера от опорного и на проходимом тайле; двое новых — не в одной клетке; занятый пол
   уводит спираль дальше, а не роняет; мир пуст — первый новый строит мир и становится
   опорным, второй встаёт рядом, а не запускает постройку заново.
   Отдельный случай: опорный оказался **не** в слоте 0 (продолжающий подключился вторым) —
   привязка всё равно идёт к нему, а не к слоту 0.
5. **Карточка.** Совпала — предлагается продолжение; не совпала или отсутствует — только
   создание; сервер остаётся авторитетным (карточка не создаёт персонажа).
6. **Меню входа на харнессе Ф3a.** Два клиента: один создаёт, второй продолжает; пока
   один не закончил, мир не тикает; оба закончили — календарь пошёл.
7. **Регресс.** Весь набор обычной сборки зелёный.

## 11. Требуемые правки родительского спека

- **§8.1** — «несколько аватаров в сейве» заменяется на «несколько сейвов персонажей
  в мире». Обещание «одиночный сейв можно отдать серверу и наоборот» становится полным
  в обе стороны, а не половинчатым.
- **§8.2** — «Вход» реализован в Ф3b, а не в Ф5, и в форме меню на каждом клиенте,
  а не автоматического поиска по имени.
- **§13** — «Клиент бесполезен без сервера» уточняется: клиент держит карточку персонажа
  (§7), чтобы опознать себя при следующем подключении. Играть по ней нельзя, сервер
  остаётся единственным источником правды — принцип тонкого клиента в силе.

## 12. Риски

1. **Персональная часть `start_game()` выделена неверно.** Персонаж без предметов
   профессии, с битым ID или размещённый мимо карты. Ловится тестами 1 и 4 (§10) плюс
   прогоном создания на свежем мире, где путь совпадает с одиночной игрой.
2. **Апстрим сам считает несколько персонажей в одном мире некорректным.**
   `src/main_menu.cpp:983` при создании второго персонажа в мире показывает: «Many game
   features will not work correctly with multiple characters in the same world». Весь
   кооп-дизайн стоит на этом пути. Hotseat доказал, что игра не разваливается, но список
   того, что именно «will not work», не составлен ни разу. **Отдельная задача фазы:
   вытащить этот список и проверить по пунктам** — миссии, фракционная репутация, лагеря,
   память карты, дневник. Это не строчка в рисках, а работа с воротами.
3. **Фолбэк размещения не находит места.** Закрыт отказом с внятным текстом (§8.2),
   а не молчаливым размещением.
4. **Старые хотсит-сейвы теряют второго персонажа.** Принято явно (§3, «Отвергнуто»).
5. **Карточка устарела.** Невозможно по построению: карточка — жетон, сервер авторитетен,
   несовпадение вырождается в предложение создать нового (§7).

## 13. Границы

- Вход и выход посреди партии, возврат после обрыва с раскруткой стека, перевод
  в follower-npc, наблюдатель после смерти, конфиг-файл сервера — Ф5.
- Создание и выбор мира, моды, спец-режимы — не вводятся; мир задаётся `--world`.
- Набор сценариев — один кооперативный на первом этапе.
- Клиентский сайдбар, разрез `widget::sample`/`layout`, тайлы — tiles-фаза.
- Персональные раскладки, звук у клиентов, шифрование и аутентификация — как в родителе,
  вне скоупа.
